## Зачем

Разработчик хочет продолжить работу с Codex на другой машине, не потеряв его
локальное состояние: проекты, то, какой чат к какому проекту относится, и историю
каждой сессии. Всё это Codex хранит в локальном каталоге (`.codex`), и одной
облачной папки недостаточно, чтобы перенести его безопасно: файл, скопированный
в момент, когда Codex его пишет, или история, выросшая на обеих машинах,
теряются без всякой ошибки.

## Как это работает

1. **Запущен ли Codex?** Ответ «не удалось определить» считается «запущен»:
   ничто, что меняет состояние, не делается оптимистично.
2. **Читать можно всегда.** `doctor`, `plan`, любые `scan`, `chats` и хранитель
   снимков работают при открытом и закрытом Codex. Результат, полученный при
   открытом Codex, помечается `volatile`, и запись не может его использовать.
3. **Запись выполняется только при закрытом Codex и всегда одинаково:**
   блокировка, которую никто другой не перехватит, долговечный журнал,
   проверенная резервная копия всего, что будет заменено, финальная проверка
   процесса прямо перед фиксацией, подготовка на том же томе, атомарная замена и
   `COMMITTED`.
4. **Любая неоднозначность останавливает операцию**, а не решается догадкой, и
   [код выхода](CLI.md#коды-выхода) говорит, какого рода была остановка.

## Установка

У ядра и командной строки нет зависимостей. Окно — необязательное дополнение.
Пока 0.2 в альфе, pip нужен `--pre`; без него он поставит 0.1. С `--upgrade`
та же команда заменит и уже установленную 0.1.

```powershell
python -m pip install --upgrade --pre "codexsync[gui]"    # командная строка и окно (PySide6)
python -m pip install --upgrade --pre codexsync           # только командная строка
```

На Windows можно вместо этого скачать готовую сборку из
[Releases](https://github.com/kroxiksut/codexSync/releases) — ни одной из них не
нужен установленный Python:

| Сборка | Windows |
|---|---|
| `codexsync-gui-<tag>-windows-amd64.zip`, `…-arm64.zip` — окно, которое выполняет и все команды | x64, ARM64 |
| `codexsync-<tag>-windows-amd64.zip`, `…-arm64.zip` — только командная строка, без Qt | x64, ARM64 |

32-битной сборки нет: сам Codex выпускается только для x64 и ARM64.

**С Node.js**, на Windows или Linux (x64 и ARM64), те же сборки приходят
через npm начиная со следующего выпуска — так же, как ставится Codex CLI:

```sh
npm install -g codexsync      # обе программы, codexsync и codexsync-gui; та же команда обновляет
npm uninstall -g codexsync    # удалить
```

Ставьте глобально, а не запускайте через `npx`: задача планировщика называет
программу там, где она установлена, а `npx` держит её в кэше, который
чистится. На Windows работающую программу нельзя заменить, поэтому перед
обновлением закройте окно и, если он запущен, остановите наблюдатель передачи.
Сборки для macOS в npm нет.

Из исходников — для разработки или ещё не выпущенного изменения:

```powershell
git clone https://github.com/kroxiksut/codexSync
cd codexSync
pip install -e ".[gui]"
```

### В Linux

Все способы ниже рабочие, «основного» нет — выбирайте, что подходит машине.
Есть root и `apt` или `dnf` — пакет; нет root — AppImage или `tar.gz`; есть
Python 3.11 или новее — `pipx` или виртуальное окружение. Пакеты, AppImage и
`tar.gz` лежат на [странице выпусков](https://github.com/kroxiksut/codexSync/releases)
начиная со следующего выпуска, для x64 (glibc 2.35 и новее: Ubuntu 22.04,
Debian 12, Fedora 36 и новее) и ARM64 (glibc 2.39 и новее: Ubuntu 24.04,
Debian 13 и новее). В каждом обе программы, `codexsync` и `codexsync-gui`.

**Пакет .deb** (Ubuntu, Debian и родственные) ставится в `/opt/codexsync`,
обе команды попадают в `PATH`, появляется пункт меню:

```sh
sudo apt install ./codexsync-<версия>-linux-amd64.deb   # установка; та же команда с файлом новее — обновление
sudo apt remove codexsync                               # удаление
```

**Пакет .rpm** (Fedora и родственные) — так же:

```sh
sudo dnf install ./codexsync-<версия>-linux-amd64.rpm   # установка; та же команда с файлом новее — обновление
sudo dnf remove codexsync                               # удаление
```

**AppImage** — один файл, который можно держать где угодно; это окно, а с
командой — командная строка:

```sh
chmod +x codexsync-<версия>-linux-amd64.AppImage
./codexsync-<версия>-linux-amd64.AppImage                          # окно
./codexsync-<версия>-linux-amd64.AppImage -c config.toml doctor    # командная строка
```

Чтобы обновить, положите новый файл по тому же пути под тем же именем (задачи
планировщика называют именно этот файл); чтобы удалить — удалите его.
`libfuse2` не нужна; где FUSE нет совсем, добавьте `--appimage-extract-and-run`.

**tar.gz** — та же папка для любого места, куда можно писать. Распакуйте её в
отдельную папку, чтобы при обновлении путь, который называют задачи
планировщика, остался прежним:

```sh
mkdir -p ~/.local/opt/codexsync
tar -xzf codexsync-<версия>-linux-amd64.tar.gz -C ~/.local/opt/codexsync --strip-components=1   # установка
rm -rf ~/.local/opt/codexsync/* && tar -xzf <файл новее> -C ~/.local/opt/codexsync --strip-components=1   # обновление
rm -rf ~/.local/opt/codexsync                                                                    # удаление
```

Программы — `~/.local/opt/codexsync/codexsync` и `codexsync-gui`. Чтобы
вызывать их по имени, сделайте ссылки в `~/.local/bin`
(`ln -s ~/.local/opt/codexsync/codexsync ~/.local/opt/codexsync/codexsync-gui ~/.local/bin/`).

**pipx** сам создаёт виртуальное окружение и следит за ним (`sudo apt install
pipx` или `sudo dnf install pipx`, затем `pipx ensurepath`):

```sh
pipx install --pip-args=--pre "codexsync[gui]"   # окно и командная строка; без [gui] — только командная строка
pipx upgrade --pip-args=--pre codexsync          # обновить
pipx uninstall codexsync                         # удалить
```

**Виртуальное окружение вручную** — системный Python отказывает в обычном
`pip install` (PEP 668); в Ubuntu и Debian сначала `sudo apt install
python3-venv`:

```sh
python3 -m venv ~/.venvs/codexsync
~/.venvs/codexsync/bin/pip install --pre "codexsync[gui]"            # установить
~/.venvs/codexsync/bin/pip install --upgrade --pre "codexsync[gui]"  # обновить
rm -rf ~/.venvs/codexsync                                            # удалить
```

Добавьте `~/.venvs/codexsync/bin` в `PATH` или вызывайте команды по этому пути.
`--pre` нужен, пока 0.2 — пре-релиз.

**Меню приложений.** Пакет `.deb` или `.rpm` сам добавляет туда CodexSync;
pipx, виртуальное окружение, AppImage и `tar.gz` — нет. Для них
`codexsync shortcut install` (или «О программе → Меню приложений» в окне)
пишет в `~/.local/share` ярлык и значок, которые запускают ту самую программу,
которой вы выполнили команду, — файл AppImage, распакованную папку,
виртуальное окружение. После переноса программы выполните команду снова;
`codexsync shortcut status` показывает, что запускает ярлык, а
`codexsync shortcut remove` убирает два записанных ею файла и ничего больше.
Если установлен пакет, команда ничего не пишет.

**Перед удалением codexSync** снимите его задачи планировщика —
`codexsync -c config.toml automation remove` (или «Автоматизация» в окне) — и
ярлык в меню, если вы его делали (`codexsync shortcut remove`):
удаление программы не трогает ни ваши задачи, ни конфиг, ни рабочую папку, ни
`.codex`, и оставшаяся задача продолжала бы запускать программу, которой нет.
Конфиг и рабочая папка остаются на месте для будущей установки.

## Первый запуск

**Окно:**

```powershell
codexsync-gui
```

Экран «Первый запуск» создаёт `config.toml`: имя машины, локальную `.codex` и
синхронизируемую папку рабочего пространства. Все экраны показаны на странице
[Окно](GUI.md).

**Командная строка:**

```powershell
codexsync init-config --output config.toml --machine-id desktop --local-state-dir C:/Users/me/.codex --workspace-root D:/Cloud/codexSync
codexsync -c config.toml doctor           # диагностика, только чтение
codexsync -c config.toml sync --dry-run   # что сделала бы синхронизация, ничего не пишет
codexsync -c config.toml sync --apply     # Codex должен быть закрыт
```

Все команды и их параметры — на странице [Командная строка](CLI.md); файл,
который пишет `init-config`, разобран по секциям в
[Конфигурации](CONFIGURATION.md).

## Принципы

- **Сначала резервная копия, при сомнении — отказ.** Неопределённость никогда не
  трактуется оптимистично.
- **Одна инстанция, один конверт.** Ровно одно место решает, можно ли менять
  состояние, и ровно один путь выполняет изменение.
- **Говорить почему, а не угадывать.** Ветка, которую нельзя классифицировать,
  проект с двумя кандидатами, поведение Codex, которое никто не наблюдал, —
  каждое сообщается кодом, а не приближается.
- **Сначала план, потом подтверждение по id.** Каждая пишущая команда сначала
  показывает план или проверочный запуск и применяет только тот id плана,
  который вы назвали. Если за это время что-то изменилось, id уже не совпадает, и
  ничего не записывается.
- **Только файлы Codex и узкая граница в них.** codexSync не пользуется API
  Codex, не читает токены, никогда не завершает Codex силой, а в его SQLite
  вносит только три правки, перечисленные в разделе
  [чего не делает](#чего-не-делает).
- **Ноль внешних зависимостей** в ядре и командной строке.

## Порядок переноса

codexSync рассчитан на строгий порядок работы между машинами:

1. Закрыть Codex на машине A.
2. Дождаться, пока облачный клиент полностью выгрузит изменения машины A.
3. Запустить codexSync на машине B.
4. Запускать Codex на машине B только после завершения синхронизации.
5. Заново войти в Codex на машине B.

Токены аутентификации не переносятся никогда. codexSync намеренно не проверяет,
закончил ли облачный провайдер синхронизацию, работает ли облачный клиент и
хватает ли места в облачной папке: это ответственность пользователя.

## Чего не делает

- Не пользуется API Codex, не перехватывает сетевой трафик и не меняет сам
  Codex.
- Не извлекает токены: после переноса в Codex нужно войти заново.
- Никогда не завершает Codex силой. С `[sync] close_codex = true` синхронизация
  просит приложение закрыться обычным способом и пишет только после того, как
  проверка процесса подтвердит, что оно закрыто; если оно не закрылось, не
  пишется ничего.
- В базы SQLite Codex — ничего, кроме трёх узких правок, каждая при закрытом
  Codex, после проверенной резервной копии и только когда нужна: состояние
  пересборки списка чатов Codex (`backfill_state`) — «пересобрать», когда вы об
  этом просите, и обратно «завершено», когда пересборка застряла и Codex не
  может запуститься (`D-032`), — для чата, у которого здесь нет названия, —
  название, которое показывает другая машина, и для чата, убранного в архив
  или возвращённого из него на другой машине, — его место и отметка архива в
  списке Codex (`D-035`).
  Никогда не создаёт и не удаляет строки чатов, не переписывает
  `session_index.jsonl` и не меняет записи проектов.
- Не синхронизирует в реальном времени: работает одна машина за раз.
- Не проверяет облачный клиент и свободное место в облачной папке.

## Платформы

- **Windows** — проверенная платформа.
- **macOS** (Apple Silicon) поддержан в коде и CI. Определение процесса Codex для
  macOS написано и покрыто тестами на записанном выводе `ps`, но пока его не
  запустили на живом Codex на Mac, платформа сообщает о себе как о
  неподдерживаемой: состояние процесса читается как «неопределённое», и все
  пишущие команды отказывают. `codexsync codex processes` показывает, что
  проверка там видит, — совпадения по номеру процесса и правилу, без путей — и
  что она прочитала бы, если бы ей доверяли; такой отчёт её и подтверждает
  ([Есть Mac?](../../README.ru.md#есть-mac)).
- **Linux** — экспериментально, как и само настольное приложение Codex для
  Linux, которое с августа 2026 года в превью. codexSync ставится из PyPI, его
  код и CI там работают. Определение процесса проверено на живом Codex под
  Ubuntu 26.04 (приложение 26.1002, 2026-10-09), поэтому пишущие команды
  открыты; полную передачу работы между Linux и другой машиной ещё не
  пробовали. Команда, которую Codex запустил в чате, может пережить само
  приложение, и пока она не закончится, Codex считается запущенным.
- **Минимальные версии:** Windows 10 (1809) или новее, Python 3.11 или новее
  для pip; окну на macOS нужна macOS 13 или новее (её поддерживает текущий
  PySide6). Python 3.14 и новее читает чаты, которые Codex хранит сжатыми
  (`.jsonl.zst`); более старые версии оставляют их заблокированными
  ([сессии](SESSIONS.md#когда-codex-сжимает-свои-чаты)). Готовые программы
  собраны на 3.14.
- CI прогоняет тесты на `windows-latest` и `macos-latest` с Python 3.11, 3.12,
  3.13 и 3.14, а на `ubuntu-latest` — экспериментально: падение там не роняет
  весь прогон.

## Что пока не подтверждено

Часть поведения Codex нельзя узнать из его файлов — только пронаблюдать. Пока
контролируемый эксперимент на расходуемом состоянии этого не зафиксирует,
codexSync сообщает о случае, а не угадывает:

| Что | Как это видно | Эксперимент |
|---|---|---|
| Общее правило, где Codex ждёт сессию, которой на этой машине никогда не было. Пока его нет, чат, который уже есть, пишется поверх своего файла, а новый — по его пути на другой машине (`[semantic] new_chats = "same_path"`, по умолчанию) | новые чаты пишутся по этому одному правилу, а `doctor` считает чаты, которых Codex не показал (`session_visibility`); с `new_chats = "keep_in_cloud"` они остаются в облачной копии (`BLOCKED_UNPROVEN_LAYOUT`) | [session-layout-adapter](../dev/experiments/session-layout-adapter.md) |
| Перезапись `session_index.jsonl` | `UNPROVEN_CONSUMER_CONTRACT` | [session-index-contract](../dev/experiments/session-index-contract.md) |
| Определение Codex на macOS (на Linux проверено) | платформа не поддерживается, запись закрыта | [process-detector-macos](../dev/experiments/process-detector-macos.md) |
| Проекты в `state_*.sqlite` | перенос проекта меняет только JSON; удаление и объединение проектов не предлагаются | [project-registry-contract](../dev/experiments/project-registry-contract.md) |

О последнем `doctor` сообщает при каждом запуске. Описания экспериментов — на
английском.
