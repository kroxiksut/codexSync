# Сессии

[English](../en/SESSIONS.md) · **Русский** · [中文](../zh/SESSIONS.md)

[← Документация](README.md)

Сессия Codex — это JSONL-файл, история, которая только растёт. Когда одна и та
же сессия продолжается на двух машинах, две копии становятся двумя *ветками*
одной истории. Если скопировать более новый файл поверх старого, всё, что
добавилось на другой машине, молча пропадёт, — поэтому обычный `sync` сессии
никогда не копирует. В окне это экран [«Сессии»](GUI.md#сессии).

## Сканирование

`sessions scan` сравнивает каждую ветку сессии на этой машине с копией в
облачной папке и классифицирует её:

- **идентична**;
- **fast-forward** в любую сторону — одна сторона является префиксом другой,
  поэтому более длинная может просто её заменить;
- **переход active ↔ archive** — та же история переместилась между `sessions/`
  и `archived_sessions/`;
- **расхождение** — обе стороны добавили разные записи;
- **копия, которой нельзя воспользоваться** (`BLOCKED_INVALID_BRANCH`), — не
  читается, обрезана, или один id сессии лежит в двух файлах
  (`LOCAL_DUPLICATE_SESSION_ID`, `REMOTE_DUPLICATE_SESSION_ID`), или копия легла
  бы на файл, который не принадлежит этой сессии (`DESTINATION_OCCUPIED`). Такая
  копия никогда не считается отсутствующей: для этой сессии ничего не пишется ни
  на одну сторону, пока файл не станет читаться, а остальные сессии она не держит.
  Одно исключение: если Codex продолжил чат в новом файле и его каталог потоков
  называет ровно один из двух, этот файл и есть чат, а второй не трогается
  (`STALE_DUPLICATE_BY_CATALOG`).

```powershell
codexsync -c config.toml sessions scan --source-machine desktop --target-machine laptop --save-plan sessions-plan.json
```

Команда не пишет ничего, кроме файла плана, и работает при открытом Codex, но
такой план помечается `volatile` и не может быть применён. Отчёт не называет ни
id сессий, ни имён тредов, ни содержимого записей: конфликт адресуется только
своим id.

## Рабочий набор

Ноутбуку, которому нужен один проект, не обязательно забирать все сессии:

```powershell
codexsync -c config.toml sessions scan --source-machine desktop --target-machine laptop --project project-orion --save-scope --save-plan sessions-plan.json
```

- `--project` и `--chat` можно повторять; `--scope-file` читает набор,
  сохранённый ранее (отсутствующий файл или файл, не являющийся сохранённым
  набором, останавливает scan с кодом `4`, а не снимает набор); `--save-scope`
  запоминает этот набор для пары машин в
  `plans/sessions-scope-<from>-<to>.json`.
- Проект — это все его чаты (закреплённые явно, найденные по пути или связанные
  правилом `[[path_mappings]]`) и порождённые ими подпотоки, включая чаты,
  появившиеся на другой машине уже после выбора набора.
- **Облачное зеркало всегда получает все сессии**, поэтому резервная копия
  никогда не становится частичной. Набор сужает только то, что пишется в
  `.codex`.
- **Набор входит в id плана**, поэтому план нельзя применить с другим набором.

Сессия, оставленная за бортом, помечается `OUT_OF_SCOPE`. Она ничего не
блокирует и несёт то, чем была бы (`WOULD_BE_…`), поэтому сводка говорит, что
именно отложено, а не просто умалчивает об этом. Набор, который не покрывает ни
одной сессии, — например, проект, в котором ещё нет чатов, — ничего не пишет в
`.codex` и помечается `WORKING_SET_MATCHES_NOTHING`; зеркало при этом всё равно
записывается полностью.

Чат, чьей рабочей папки нет на этой машине — обычно это проект, который лежит
вне синхронизируемой папки, — помечается `CWD_ABSENT_HERE`, а `sessions scan`
считает такие чаты в `cwd_absent_here`. Папка ищется там, куда её переносит
`[[path_mappings]]`; если два правила расходятся, чат помечается
`CWD_MAPPING_AMBIGUOUS`, а не угадывается. Пометка ничего не блокирует: она для
того, чтобы оставить такие проекты вне рабочего набора, а не узнать об этом,
открыв чат. Папка, созданная после сканирования, меняет id плана, и применение
попросит просканировать заново.

## Расхождения

Расхождение никогда не сливается — ни чередования записей, ни их сортировки.
Остаётся одна из двух версий, а другая целиком уходит в пакет конфликта до
того, как что-либо будет заменено. Какая именно — решает
[`conflict.policy`](SYNC.md#конфликты) ([D-027](../dev/DECISIONS.md)): по
умолчанию версия, чьё последнее сообщение позже, либо всегда версия этой
машины, либо всегда облачная (`--conflict-policy` — на одно сканирование).
Такой элемент помечается `RESOLVED_BY_RULE`. При `manual_abort`, а также для
двух версий, закончившихся в один и тот же момент (`RULE_CANNOT_DECIDE`), план
блокируется, пока не записано решение:

```powershell
codexsync -c config.toml sessions resolve --plan sessions-plan.json --conflict <conflict-id> --choice KEEP_LOCAL --output resolutions.json
codexsync -c config.toml sessions scan --source-machine desktop --target-machine laptop --resolutions resolutions.json --save-plan sessions-plan.json
```

`--choice` принимает `KEEP_LOCAL`, `KEEP_REMOTE` или `DEFER`. `DEFER` оставляет
конфликт открытым, а открытый конфликт отклоняет **весь** `sessions apply`, а не
только эту сессию, — откладывайте только то, что решите до следующего apply.
`sessions scan` завершается с кодом `2` ровно тогда, когда в плане есть такое
решение (конфликт или столкновение целей); сессия, заблокированная только
неподтверждённой раскладкой или каталогом SQLite, пропускается при apply и код
выхода не меняет.

Решение привязано
к точным байтам обеих веток: если любая из них потом изменится, решение
отклоняется как `STALE_RESOLUTION`, а не применяется к истории, которую вы не
видели. Записанное решение, включая `DEFER`, всегда важнее политики. В окне
экран «Сессии» решает все конфликты сканирования сразу по одному правилу
(*Все конфликты сразу:*) или по одному.

Длинный чат Codex продолжает во втором файле,
`rollout-…-<id>_<other id>.jsonl`, который начинается с того же id чата и
указывает, откуда он продолжается (`history_base`). Чат — это цепочка файлов:
каждый файл переносится сам по себе (файл-продолжение помечается `HISTORY_PAGE`), первый
продолжает расти, как прежде, и ни один из них не конфликтует с другим.

Равенство записей определяется сырыми байтами. Каноническая форма JSON
используется только там, где она заведомо однозначна, поэтому две разные записи
никогда не схлопнутся в одну.

### Когда Codex переписал свои сессии

В сентябре 2026 года десктопная сборка Codex переписала все существующие файлы
сессий в новый формат записей: каждая запись пронумерована (`ordinal`),
сообщения переехали в другие поля, а часть записей по дороге пропала — ходы,
которые вы откатывали, повторные записи `session_meta`, вставленные инструкции.
Время изменения файлов при этом сохранилось старое. Облачное зеркало, записанное
до этого, расходится с каждой сессией, которую хранит.

Такой конфликт помечается `FORMAT_MIGRATION` вместе с `NEWER_FORMAT_LOCAL` или
`NEWER_FORMAT_REMOTE` — только расхождение содержимого, но не отсутствие базы, а `doctor` предупреждает (`session_format`), пока одна из
сторон остаётся в старом формате. Это по-прежнему конфликт — две копии не одна и
та же история, — но одно решение покрывает их все:

```powershell
codexsync -c config.toml sessions resolve --plan sessions-plan.json --format-migrations --output resolutions.json
```

Для каждого оно оставляет копию в новом формате и привязано к байтам, как любое
другое решение. Конфликт с пометкой `OLDER_FORMAT_HAS_LATER_RECORDS` оно не
трогает: там в старой копии есть запись новее всего, что есть в новой, — это
может быть работа, сделанная в другом месте до обновления, — поэтому ему нужно
своё `--conflict … --choice …`. В окне это кнопка **Оставить новый формат для
всех**.

При применении плана каждая старая копия, которую предстоит перезаписать,
сохраняется один раз и в сжатом виде в `superseded/` внутри `semantic.root_dir` —
единственном месте, где пропавшие записи ещё существуют. В отличие от пакета
конфликта, победившая копия второй раз не хранится.

## Применение плана

Для применения нужны закрытый Codex и точный id плана. Сначала план
перестраивается из текущего состояния, и его id должен совпасть, поэтому любое
изменение после сканирования — выросшая ветка, новый конфликт, устаревшее
решение — отклоняет применение:

```powershell
codexsync -c config.toml sessions apply --plan sessions-plan.json --confirm-plan <plan-id> --dry-run
codexsync -c config.toml sessions apply --plan sessions-plan.json --confirm-plan <plan-id> --resolutions resolutions.json
```

- Ветка переносится **целиком**: к месту назначения ничего не дописывается, и
  истории не перемешиваются. Источник только читается; место назначения до
  замены попадает в проверенную резервную копию.
- Ветка, проигравшая решение, дополнительно сохраняется в неизменяемом **пакете
  конфликта (conflict bundle)** в `semantic.root_dir`, в `conflicts/<id конфликта>`
  — том самом id, который вы разрешали, — и обе копии перехешируются до фиксации.
  Резервные копии удаляются по сроку хранения; пакет гарантирует, что расходящаяся история никогда не
  останется единственной копией в том, что истекает.
- Применение **частичное по замыслу**. Конфликт или коллизия цели
  останавливает весь план, потому что каждый из них — решение, которое можете
  принять только вы. Элементы, заблокированные неподтверждённой раскладкой,
  каталогом SQLite или копией, которой нельзя воспользоваться, попадают в отчёт и
  остаются на месте.
- Чат, который на одной машине отправили в архив (или вернули из архива), так
  же переносится на другой (`D-023`). Какая сторона сдвинулась, читается из
  записи этой машины о последнем согласии, а не из часов; машина без своей
  записи следует облачной копии. Чат пишется туда, где его держит другая машина,
  а старый файл удаляется — после того как он лёг в проверенную резервную копию,
  в том же конверте. В `.codex` для этого каталог потоков должен называть
  переносимый файл. Чат, который на одной машине архивировали, а на другой
  продолжили, — решение за вами (`ARCHIVED_AND_CONTINUED`). Строка каталога
  называет старое место, пока Codex её не обновит; `doctor` считает такие чаты
  в `session_visibility`.

### Запись в `.codex`

Где рантайм Codex ищет файл сессии — свойство самого рантайма: положите файл в
другое место, и сессия станет невидимой без всякой ошибки. Поэтому запись
**в** `.codex` идёт одним из двух путей.

**Чат, который на этой машине уже есть**, — тот, что продолжили на другой
машине, — записывается поверх своего же файла (`IN_PLACE`). Каталог потоков
Codex (`state_*.sqlite`) называет этот файл, так что путь не выбирается и
ничего о раскладке не угадывается: более новая копия того же чата, с его
продолжением, заменяет старую — после того как старая легла в проверенную
резервную копию. Это разрешено, только если каталог называет ровно этот файл
для этого чата, а чат на обеих машинах активен или на обеих в архиве. Иначе
элемент остаётся `BLOCKED_UNPROVEN_LAYOUT` с кодом причины:
`IN_PLACE_CATALOG_ABSENT`, `SESSION_NOT_IN_CATALOG`, `CATALOG_PLACES_ELSEWHERE`,
`CATALOG_UNREADABLE`, `IN_PLACE_STATE_CHANGES`, `IN_PLACE_ARCHIVE_FLAG_DIFFERS`
или `IN_PLACE_CONTAINER`.

В том же каталоге Codex хранит заголовок, превью и время каждого чата, а
codexSync его никогда не пишет. Поэтому список чатов может показывать старые
значения, пока Codex их не обновит; сам разговор читается из файла.

**Чат, которого на этой машине никогда не было**, решает одна настройка:

```toml
[semantic]
new_chats = "same_path"   # same_path | keep_in_cloud
```

- `keep_in_cloud` оставляет его в облачной копии с пометкой
  `BLOCKED_UNPROVEN_LAYOUT`: где Codex ждёт файл нового чата, не доказано
  [контролируемым экспериментом](../dev/experiments/session-layout-adapter.md).
- `same_path` (по умолчанию) записывает его в `.codex` по тому пути, который у него на
  машине-источнике, относительно `.codex` (`sessions/<год>/<месяц>/<день>/…`
  или `archived_sessions/…`). Так делала 0.1, копируя `sessions/` целиком. Имя
  пользователя и диск не важны: путь относительный. Каждый такой элемент несёт
  код `NEW_CHAT_SAME_PATH`. Файл, который уже лежит по этому пути, никогда не
  перезаписывается (`DESTINATION_OCCUPIED`). Если каталог помещает чат в другое
  место или не читается, запись тоже отклоняется (`BLOCKED_UNSUPPORTED_BACKEND`).

Список чатов Codex берёт из своего каталога потоков. Codex один раз заполняет
его по файлам чатов, а дальше ведёт сам. Файла, записанного позже, — а это
каждый чат с другой машины — в каталоге нет, и Codex его не показывает. Поэтому
полная синхронизация просит Codex пересобрать список по файлам (`D-024`):
codexSync возвращает одну строку состояния к значению, с которым Codex её
создаёт, после проверенной резервной копии каталога, а Codex при следующем
запуске сам вносит в список все чаты. Этот запуск дольше обычного. Сам чат в
каталог codexSync не пишет никогда. `codexsync sessions catalogue` показывает
файлы чатов, которых нет в списке Codex, а с `--confirm-plan` делает ту же
просьбу отдельно. Просьба делается один раз на один набор файлов; если Codex и
после этого какие-то не показывает, синхронизация так и скажет, а не будет
просить снова. `doctor` показывает то же число в `session_visibility`;
`not_listed=0` значит, что видны все.

**Названия** чата в его файле тоже нет: Codex держит его только в этом каталоге,
поэтому перенесённый чат сначала показывается по первому сообщению. Поэтому
каждая машина публикует названия своих чатов в `chat-names` рядом с манифестом,
а полная синхронизация проставляет название с другой машины чату, у которого
здесь своего названия нет, — и никогда поверх названия, данного здесь
(`D-025`). Чат, который Codex внесёт в список только при следующем запуске,
получит название при синхронизации после этого. `codexsync sessions names`
показывает план, а с `--confirm-plan` делает то же отдельно.

Рабочая папка чата на этой машине может лежать в другом месте. Файл ради этого
не меняется (байты записи — её идентичность): задайте соответствие папок в
`[[path_mappings]]` или переместите проект, см. [Проекты](PROJECTS.md).

Запись **в сторону облачной папки** не ограничена: эту копию не читает ни один
Codex, поэтому ветка, которой в зеркале ещё нет, сохраняет свой локальный
относительный путь. Ветка, которая там уже есть, перезаписывается на своём месте,
даже если локальная копия лежит в другом (`MIRROR_PATH_KEPT`), потому что
второй файл одной сессии выбросил бы оба из всех последующих планов; переносит
его только перенос в архив или из архива (`MOVES_BRANCH`). Именно это
позволяет пересобрать устаревшее или отсутствующее зеркало.

## Облачное зеркало

Поскольку зеркало не читает ни один рантайм, ветка может лежать там в сжатом
виде:

```toml
[semantic]
root_dir = "${workspace_root}/semantic"   # манифесты веток и пакеты конфликтов
mirror_compression = "xz"                 # none | gzip | xz
```

- `xz` сжимает настоящие данные сессий примерно до трети. Это касается только
  зеркала: ветка, записанная обратно в `.codex`, всегда обычный JSONL.
- **Сжатие — свойство контейнера, а не истории.** Хеши веток, число записей и
  любое сравнение берутся из распакованного потока, поэтому сжатая копия в
  зеркале `IDENTICAL` обычной локальной ветке.
- Настройка действует для ветки, которой в зеркале ещё нет. Ветка, которая там
  уже лежит, сохраняет свой контейнер (`MIRROR_CONTAINER_KEPT`): контейнер
  входит в имя файла, а два имени для одной сессии заставили бы каталог
  исключить эту сессию из всех последующих планов.
- Контейнер входит в id плана, поэтому смена настройки делает существующий план
  недействительным, а не переименовывает места назначения под уже данным вами
  подтверждением.

## Индекс сессий

`session_index.jsonl` — журнал добавлений и обновлений, а не список
существующих сессий: один id может встречаться на нескольких строках, у сессии
может не быть строки, а строка может называть уже удалённый файл. Ничто из этого
не ошибка, и codexSync никогда его не «чистит».

```powershell
codexsync -c config.toml sessions index
```

Отчёт показывает, что лежит в индексе каждой стороны и где они расходятся.
Команда только читает, работает при открытом Codex и не называет ни id сессий,
ни имён тредов.

- У повторяющегося id два правдоподобных прочтения — побеждает последняя строка
  или наибольший `updated_at`, — и они расходятся ровно тогда, когда часы шли
  назад. Это сообщается как `REDUCTION_AMBIGUOUS`; `doctor` делает ту же
  проверку.
- Если две стороны хранят разные записи для одной сессии, это расхождение
  переименования — решение, а не слияние.
- Индекс не перезаписывается, пока то, как его читает рантайм, не подтверждено
  (`UNPROVEN_CONSUMER_CONTRACT`,
  [эксперимент](../dev/experiments/session-index-contract.md)).
