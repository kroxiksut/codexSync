# Сессии

[English](../en/SESSIONS.md) · **Русский** · [中文](../zh/SESSIONS.md)

[← Документация](README.md)

Сессия Codex — это JSONL-файл, история, которая только растёт. Когда одна и та
же сессия продолжается на двух машинах, две копии становятся двумя *ветками*
одной истории. Если скопировать более новый файл поверх старого, всё, что
добавилось на другой машине, молча пропадёт, — поэтому обычный `sync` сессии
никогда не копирует. В окне это экран [«Сессии»](GUI.md#сессии).

## Сканирование

`sessions scan` сравнивает каждую ветку сессии на этой машине с копией в
облачной папке и классифицирует её:

- **идентична**;
- **fast-forward** в любую сторону — одна сторона является префиксом другой,
  поэтому более длинная может просто её заменить;
- **переход active ↔ archive** — та же история переместилась между `sessions/`
  и `archived_sessions/`;
- **расхождение** — обе стороны добавили разные записи.

```powershell
codexsync -c config.toml sessions scan --source-machine desktop --target-machine laptop --save-plan sessions-plan.json
```

Команда не пишет ничего, кроме файла плана, и работает при открытом Codex, но
такой план помечается `volatile` и не может быть применён. Отчёт не называет ни
id сессий, ни имён тредов, ни содержимого записей: конфликт адресуется только
своим id.

## Рабочий набор

Ноутбуку, которому нужен один проект, не обязательно забирать все сессии:

```powershell
codexsync -c config.toml sessions scan --source-machine desktop --target-machine laptop --project project-chloya --save-scope --save-plan sessions-plan.json
```

- `--project` и `--chat` можно повторять; `--scope-file` читает набор,
  сохранённый ранее; `--save-scope` запоминает этот набор для пары машин в
  `plans/sessions-scope-<from>-<to>.json`.
- Проект — это все его чаты (закреплённые явно, найденные по пути или связанные
  правилом `[[path_mappings]]`) и порождённые ими подпотоки, включая чаты,
  появившиеся на другой машине уже после выбора набора.
- **Облачное зеркало всегда получает все сессии**, поэтому резервная копия
  никогда не становится частичной. Набор сужает только то, что пишется в
  `.codex`.
- **Набор входит в id плана**, поэтому план нельзя применить с другим набором.

Сессия, оставленная за бортом, помечается `OUT_OF_SCOPE`. Она ничего не
блокирует и несёт то, чем была бы (`WOULD_BE_…`), поэтому сводка говорит, что
именно отложено, а не просто умалчивает об этом.

Чат, чьей рабочей папки нет на этой машине — обычно это проект, который лежит
вне синхронизируемой папки, — помечается `CWD_ABSENT_HERE`, а `sessions scan`
считает такие чаты в `cwd_absent_here`. Папка ищется там, куда её переносит
`[[path_mappings]]`; если два правила расходятся, чат помечается
`CWD_MAPPING_AMBIGUOUS`, а не угадывается. Пометка ничего не блокирует: она для
того, чтобы оставить такие проекты вне рабочего набора, а не узнать об этом,
открыв чат. Папка, созданная после сканирования, меняет id плана, и применение
попросит просканировать заново.

## Расхождения

Расхождение никогда не разрешается автоматически — ни чередования записей, ни
сортировки по времени, ни «побеждает новее». Обе ветки остаются как есть, а
план блокируется, пока не записано решение:

```powershell
codexsync -c config.toml sessions resolve --plan sessions-plan.json --conflict <conflict-id> --choice KEEP_LOCAL --output resolutions.json
codexsync -c config.toml sessions scan --source-machine desktop --target-machine laptop --resolutions resolutions.json --save-plan sessions-plan.json
```

`--choice` принимает `KEEP_LOCAL`, `KEEP_REMOTE` или `DEFER`. Решение привязано
к точным байтам обеих веток: если любая из них потом изменится, решение
отклоняется как `STALE_RESOLUTION`, а не применяется к истории, которую вы не
видели.

Равенство записей определяется сырыми байтами. Каноническая форма JSON
используется только там, где она заведомо однозначна, поэтому две разные записи
никогда не схлопнутся в одну.

### Когда Codex переписал свои сессии

В сентябре 2026 года десктопная сборка Codex переписала все существующие файлы
сессий в новый формат записей: каждая запись пронумерована (`ordinal`),
сообщения переехали в другие поля, а часть записей по дороге пропала — ходы,
которые вы откатывали, повторные записи `session_meta`, вставленные инструкции.
Время изменения файлов при этом сохранилось старое. Облачное зеркало, записанное
до этого, расходится с каждой сессией, которую хранит.

Такой конфликт помечается `FORMAT_MIGRATION` вместе с `NEWER_FORMAT_LOCAL` или
`NEWER_FORMAT_REMOTE`, а `doctor` предупреждает (`session_format`), пока одна из
сторон остаётся в старом формате. Это по-прежнему конфликт — две копии не одна и
та же история, — но одно решение покрывает их все:

```powershell
codexsync -c config.toml sessions resolve --plan sessions-plan.json --format-migrations --output resolutions.json
```

Для каждого оно оставляет копию в новом формате и привязано к байтам, как любое
другое решение. Конфликт с пометкой `OLDER_FORMAT_HAS_LATER_RECORDS` оно не
трогает: там в старой копии есть запись новее всего, что есть в новой, — это
может быть работа, сделанная в другом месте до обновления, — поэтому ему нужно
своё `--conflict … --choice …`. В окне это кнопка **Оставить новый формат для
всех**.

При применении плана каждая старая копия, которую предстоит перезаписать,
сохраняется один раз и в сжатом виде в `superseded/` внутри `semantic.root_dir` —
единственном месте, где пропавшие записи ещё существуют. В отличие от пакета
конфликта, победившая копия второй раз не хранится.

## Применение плана

Для применения нужны закрытый Codex и точный id плана. Сначала план
перестраивается из текущего состояния, и его id должен совпасть, поэтому любое
изменение после сканирования — выросшая ветка, новый конфликт, устаревшее
решение — отклоняет применение:

```powershell
codexsync -c config.toml sessions apply --plan sessions-plan.json --confirm-plan <plan-id> --dry-run
codexsync -c config.toml sessions apply --plan sessions-plan.json --confirm-plan <plan-id> --resolutions resolutions.json
```

- Ветка переносится **целиком**: к месту назначения ничего не дописывается, и
  истории не перемешиваются. Источник только читается; место назначения до
  замены попадает в проверенную резервную копию.
- Ветка, проигравшая решение, дополнительно сохраняется в неизменяемом **пакете
  конфликта (conflict bundle)** в `semantic.root_dir`. Резервные копии удаляются
  по сроку хранения; пакет гарантирует, что расходящаяся история никогда не
  останется единственной копией в том, что истекает.
- Применение **частичное по замыслу**. Конфликт или коллизия цели
  останавливает весь план, потому что каждый из них — решение, которое можете
  принять только вы. Элементы, заблокированные неподтверждённой раскладкой или
  каталогом SQLite, попадают в отчёт и остаются на месте.
- Переходы active ↔ archive в 0.2 сообщаются, но не применяются: перемещение
  требует удаления, а codexSync никогда не удаляет файл сессии.

### Запись в `.codex`

Где рантайм Codex ищет файл сессии — свойство самого рантайма: положите файл в
другое место, и сессия станет невидимой без всякой ошибки. Поэтому запись
**в** `.codex` требует двух вещей:

- **подтверждённой раскладки назначения.** Пока контролируемый эксперимент её
  не зафиксировал, такой элемент помечается `BLOCKED_UNPROVEN_LAYOUT`
  ([эксперимент](../dev/experiments/session-layout-adapter.md));
- **строки в каталоге потоков Codex** (`state_*.sqlite`), называющей ровно этот
  файл. codexSync не пишет в SQLite, поэтому сессию, о которой каталог никогда
  не слышал, сделать видимой нельзя; она помечается
  `UNSUPPORTED_STATE_BACKEND`.

Запись **в сторону облачной папки** не ограничена: эту копию не читает ни один
Codex, поэтому ветка сохраняет свой локальный относительный путь. Именно это
позволяет пересобрать устаревшее или отсутствующее зеркало.

## Облачное зеркало

Поскольку зеркало не читает ни один рантайм, ветка может лежать там в сжатом
виде:

```toml
[semantic]
root_dir = "${workspace_root}/semantic"   # манифесты веток и пакеты конфликтов
mirror_compression = "xz"                 # none | gzip | xz
```

- `xz` сжимает настоящие данные сессий примерно до трети. Это касается только
  зеркала: ветка, записанная обратно в `.codex`, всегда обычный JSONL.
- **Сжатие — свойство контейнера, а не истории.** Хеши веток, число записей и
  любое сравнение берутся из распакованного потока, поэтому сжатая копия в
  зеркале `IDENTICAL` обычной локальной ветке.
- Настройка действует для ветки, которой в зеркале ещё нет. Ветка, которая там
  уже лежит, сохраняет свой контейнер (`MIRROR_CONTAINER_KEPT`): контейнер
  входит в имя файла, а два имени для одной сессии заставили бы каталог
  исключить эту сессию из всех последующих планов.
- Контейнер входит в id плана, поэтому смена настройки делает существующий план
  недействительным, а не переименовывает места назначения под уже данным вами
  подтверждением.

## Индекс сессий

`session_index.jsonl` — журнал добавлений и обновлений, а не список
существующих сессий: один id может встречаться на нескольких строках, у сессии
может не быть строки, а строка может называть уже удалённый файл. Ничто из этого
не ошибка, и codexSync никогда его не «чистит».

```powershell
codexsync -c config.toml sessions index
```

Отчёт показывает, что лежит в индексе каждой стороны и где они расходятся.
Команда только читает, работает при открытом Codex и не называет ни id сессий,
ни имён тредов.

- У повторяющегося id два правдоподобных прочтения — побеждает последняя строка
  или наибольший `updated_at`, — и они расходятся ровно тогда, когда часы шли
  назад. Это сообщается как `REDUCTION_AMBIGUOUS`; `doctor` делает ту же
  проверку.
- Если две стороны хранят разные записи для одной сессии, это расхождение
  переименования — решение, а не слияние.
- Индекс не перезаписывается, пока то, как его читает рантайм, не подтверждено
  (`UNPROVEN_CONSUMER_CONTRACT`,
  [эксперимент](../dev/experiments/session-index-contract.md)).
