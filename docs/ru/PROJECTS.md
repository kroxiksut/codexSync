# Проекты и чаты

[English](../en/PROJECTS.md) · **Русский** · [中文](../zh/PROJECTS.md)

[← Документация](README.md)

Проект Codex — это папка (его *корень*) и принадлежащие ему чаты. После переезда
на другую машину или переноса папки пути перестают совпадать, и чаты молча
перестают показываться под своим проектом. Эта страница о том, как их найти,
закрепить, починить привязки после переезда и перенести файлы проекта. В окне
это экраны [«Привязка чатов»](GUI.md#привязка-чатов) и
[«Проекты»](GUI.md#проекты).

> [!NOTE]
> Codex хранит проекты ещё и в `state_*.sqlite`, а записи проектов там codexSync
> никогда не меняет.
> Поэтому перенос или смена корня проекта переписывает корень только в
> `.codex-global-state.json`, а удаление и объединение проектов не предлагаются.
> `doctor` сообщает об этом при каждом запуске
> ([эксперимент](../dev/experiments/project-registry-contract.md)).

## Чаты

`chats tree` выводит проекты с их чатами, а в конце — чаты без проекта.
`chats list` показывает то же самое с фильтрами. Обе команды только читают и
работают при открытом Codex.

```powershell
codexsync -c config.toml chats tree
codexsync -c config.toml chats list --text "parser" --limit 20
codexsync -c config.toml chats list --project none
```

`chats list` также принимает `--association`, `--since`/`--until`,
`--sub-threads` (потоки, порождённые агентами, по умолчанию скрыты) и `--json`.

Каждая строка говорит, *почему* чат находится там, где находится, и три причины
ведут себя по-разному:

| Метка | Связь | Значение |
|---|---|---|
| `pinned` — закреплён явно | `BOUND` | Явная запись в `thread-project-assignments`. Следует за проектом, если его путь меняется. |
| `by path` — найден по пути | `DERIVED` | Записи нет; записанная папка чата лежит под корнем проекта. При переносе проекта чат остаётся позади. |
| `by rule!` — только по правилу | `DERIVED_VIA_MAPPING` | Папка называет путь *другой машины*, и с проектом здесь её связывает только правило `[[path_mappings]]`. Codex эти правила не читает, поэтому показывает такой чат вообще без проекта. |

Последний случай — именно то, что даёт переезд между машинами: на ноутбуке
проект лежит на `C:`, а каждый чат, пришедший с настольной машины, по-прежнему
записывает `D:`. Показать ровно такие чаты:

```powershell
codexsync -c config.toml chats list --source-machine desktop --target-machine laptop --association DERIVED_VIA_MAPPING
```

## Перенос чатов в проект

Перенос начинается с предпросмотра. `chats move` ничего не пишет, пока вы не
повторите команду с напечатанным id плана, а для записи Codex должен быть
закрыт:

```powershell
codexsync -c config.toml chats move --chat 3f9c2e71 --to Atlas
codexsync -c config.toml chats move --chat 3f9c2e71 --to Atlas --confirm <plan-id>
```

- Файла плана нет: id покрывает решения *и* точные байты состояния, из которого
  они прочитаны, поэтому перестаёт совпадать, как только что-либо изменится.
- Запись — одна привязка на чат в той форме, которую использует обнаруженная
  схема, в том же конверте, что и любая другая запись: сначала проверенная
  полная резервная копия, проверка процесса непосредственно перед заменой и
  проверенный откат, если после неё что-то пошло не так.
- `--dry-run` выполняет все проверки и ничего не пишет.

## Проекты между машинами

Боковая панель Codex — проекты, их порядок, закреплённые и то, какие чаты
явная привязка кладёт в проект, — часть `.codex-global-state.json`. В этом же
файле лежит и то, что принадлежит одной машине (положение окна, идентификаторы
удалённого управления, отметки миграций), поэтому целиком он не копируется
никогда. Вместо этого каждая полная синхронизация переносит его **проектную
часть**:

- каждая машина публикует свой список проектов в папку `projects` рядом с
  `state.manifest_file` (один самопроверяющийся файл на машину, пишет его
  только она);
- следующая машина его **сливает**: проект сопоставляется по id, затем по
  папке (через [`[[path_mappings]]`](CONFIGURATION.md#path_mappings)); проект,
  которого здесь нет, добавляется ровно таким, каким его записал Codex на
  другой машине;
- **ничего не удаляется** — проект, который есть только на этой машине,
  остаётся на своём месте;
- для проектов, которые есть на обеих машинах, закрепление, порядок и
  привязки чатов берутся с другой машины, но только из списка, который эта
  машина ещё не принимала, — неизменившийся список не накатывается повторно
  поверх того, что поменяли здесь;
- проект, папки которого на этой машине нет, всё равно добавляется, и
  синхронизация об этом говорит — создайте папку или добавьте сопоставление
  путей.

Это часть `handoff sync` и кнопки **Синхронизировать** в окне. Вручную:

```powershell
codexsync -c config.toml projects sync                        # предпросмотр: что добавится, id плана
codexsync -c config.toml projects sync --confirm-plan <id>    # Codex закрыт: слить и опубликовать список этой машины
```

Запись проходит через тот же конверт, что и любое изменение глобального
состояния: Codex закрыт, сначала проверенная резервная копия, откат через
[`recover`](RECOVERY.md#прерванные-операции), если что-то пошло не так. Codex
хранит проекты ещё и в `state_*.sqlite`, а записи проектов там codexSync не
меняет никогда; боковая панель следует JSON-файлу.

### Папки проектов

Чаты и список проектов переносятся, а собственные файлы проекта — нет: они в
git, в облачной папке или только на одном диске. Чат, продолженный на старой
копии кода, работает не с теми файлами, поэтому каждая полная синхронизация ещё
и сравнивает папки проектов (`D-026`). Каждая машина публикует, что лежит в её
папках, в `project-files` рядом с манифестом: для git-папки — коммит, ветку и
есть ли незакоммиченные изменения; для любой другой — каждый файл с размером
и SHA-256 (папки инструментов вроде `node_modules` или `.venv` не учитываются,
файлы больше 100 МБ сравниваются по размеру и времени). Заново читаются только
файлы, у которых изменились размер или время: хэши кэшируются на каждой машине,
вне рабочей папки. Вместе с проектом публикуется, когда там последний раз
менялся его чат. Следующая машина сравнивает все проекты — папку может поменять
что угодно — и говорит, начиная с проектов, чаты которых продолжались там:

- последнего коммита с другой машины здесь нет — подтяните его;
- на обеих машинах сделаны разные коммиты — слейте их;
- на другой машине остались незакоммиченные изменения, которых здесь нет;
- в обычной папке на другой машине есть файлы, изменённые позже, файлы, которых
  здесь нет, или файлы, удалённые там, но ещё лежащие здесь, — `projects files`
  перечислит их;
- папки здесь нет — или она есть здесь, но её нет там.

Папки и файлы появляются и исчезают в любой момент, поэтому ничего не берётся из
прошлой проверки: каждая проверка читает папки заново и публикует сторону этой
машины — полная синхронизация, `projects files` и окно при **каждом запуске**;
так машина, которая ещё не синхронизировалась, всё равно сообщает остальным,
что у неё лежит. Удалённый на машине файл помнится в её публикации 90 дней,
чтобы следующая машина отличала «удалён там» от «добавлен здесь».

Ничего не копируется, не подтягивается и не блокируется, а работа, которая есть
только здесь, ничего не вызывает. Git используется, если установлен, и только
для чтения: индекс он не трогает. В окне **Проекты → Папки проектов** показывает
каждый проект, доехавший не полностью, с файлами под ним, а в результате полной
синхронизации есть кнопка туда. `codexsync -c config.toml projects files`
печатает тот же список со всеми файлами — запустите после `git pull`, чтобы
увидеть, что предупреждение ушло (`--all` покажет все проекты).

## Ремонт после переезда на другую машину

Когда папка проекта переезжает — переименована, перенесена на другой диск или
открыта на второй машине под другим корнем, — Codex её теряет. Укажите правилом
[`[[path_mappings]]`](CONFIGURATION.md#path_mappings), где теперь находится
старый префикс, и просканируйте:

```powershell
codexsync -c config.toml repair-projects scan --source-machine desktop --target-machine laptop --save-plan repair-plan.json
codexsync -c config.toml repair-projects apply --plan repair-plan.json --confirm-plan <plan-id> --dry-run
codexsync -c config.toml repair-projects apply --plan repair-plan.json --confirm-plan <plan-id>
```

План строится из того, что на самом деле записано в сессиях, пропущенного через
правила соответствия. Проверочный запуск выполняет все отказы настоящего
применения, включая проверку процесса.

- **`REMAP_ROOT`.** Если *записанный* корень существующего проекта, пропущенный
  через то же правило, попадает в папку, на которую теперь указывают сессии,
  план меняет корень этого проекта, а не создаёт второй. Переписывается только
  это одно значение пути, поэтому у проекта остаются id и имя.
- **Смена корня никогда не применяется в одиночку.** Чаты, созданные до
  переезда, записали старую папку, и перенос корня из неё сделал бы их
  невидимыми. Поэтому каждая сессия, всё ещё лежащая под старым корнем, тоже
  закрепляется за проектом. Если какой-то такой чат остался бы без привязки,
  план сообщает `REMAP_ORPHANS_SESSIONS`, и применение отклоняется. Чат под
  старым корнем, который уже принадлежит *другому* проекту (вложенному или тому,
  куда вы его перенесли), не забирается: план сообщает
  `REMAP_SESSION_BOUND_ELSEWHERE` и отказывает, пока вы не решите, где ему место.
- **Чат, чья папка здесь не проект,** показывается как `SKIP_NO_PROJECT` и
  остаётся как есть. Записи проектов настольной сборки содержат поля, которые
  codexSync не выдумывает, поэтому проект там он не создаёт никогда: создайте его
  в Codex и повторите сканирование. Такой чат больше не блокирует остальной план.
- **Два кандидата**, которые оба отображаются на один новый корень,
  сообщаются как `AMBIGUOUS_PROJECT`, и ничего не применяется.
- **Внутри файла сессии ничего не правится.** Сырые байты записи — её
  идентичность при сравнении веток, поэтому переписанный там `cwd` сделал бы одну
  и ту же историю на двух машинах навсегда расходящейся.

## Перенос файлов проекта

`project-move` сам переносит проект на одной машине:

```powershell
codexsync -c config.toml project-move scan --project Atlas --to D:/Work/atlas --save-plan move.json
codexsync -c config.toml project-move apply --plan move.json --confirm-plan <plan-id> --dry-run
codexsync -c config.toml project-move apply --plan move.json --confirm-plan <plan-id>
```

1. Проект копируется в папку, которой ещё не существует.
2. Хеш каждого скопированного файла сверяется с планом.
3. Проверенная копия переименовывается на место.
4. Только после этого меняется корень проекта и закрепляются чаты, которые
   попадали в проект по пути.

**Старая папка никогда не изменяется и не удаляется** — удалить её, проверив
копию, решаете вы.

Сканирование отклоняет цель, которая уже существует, лежит внутри проекта (или
проект внутри неё), пересекается с `.codex`, зеркалом, резервными копиями, temp
или хранилищами снимков либо принадлежит другому проекту, а также проект, в
котором есть символические ссылки, junction-точки или нечитаемые файлы.
Облачные заглушки (например, Яндекс.Диска) — обычные файлы, а не ссылки. Если
фиксация состояния не удалась после копирования, проверенная копия остаётся, и
новое сканирование её распознаёт (`copy_complete`), так что повторный запуск
только обновляет Codex.

Копирование не ограничено лимитом Windows в 260 символов на путь, поэтому
глубокий `.git` переезжает и там, где длинные пути выключены. Но если на такой
машине самый длинный путь в новой папке дотягивает до этого лимита,
сканирование об этом скажет: программа, не умеющая работать с длинными путями,
может не открыть такой файл. Копию, оставленную прежней неудачной попыткой того
же переезда, сканирование показывает, а переезд удаляет её перед новым
копированием.
