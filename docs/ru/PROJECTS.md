# Проекты и чаты

[English](../en/PROJECTS.md) · **Русский** · [中文](../zh/PROJECTS.md)

[← Документация](README.md)

Проект Codex — это папка (его *корень*) и принадлежащие ему чаты. После переезда
на другую машину или переноса папки пути перестают совпадать, и чаты молча
перестают показываться под своим проектом. Эта страница о том, как их найти,
закрепить, починить привязки после переезда и перенести файлы проекта. В окне
это экраны [«Привязка чатов»](GUI.md#привязка-чатов) и
[«Проекты»](GUI.md#проекты).

> [!NOTE]
> Codex хранит проекты ещё и в `state_*.sqlite`, куда codexSync никогда не пишет.
> Поэтому перенос или смена корня проекта переписывает корень только в
> `.codex-global-state.json`, а удаление и объединение проектов не предлагаются.
> `doctor` сообщает об этом при каждом запуске
> ([эксперимент](../dev/experiments/project-registry-contract.md)).

## Чаты

`chats tree` выводит проекты с их чатами, а в конце — чаты без проекта.
`chats list` показывает то же самое с фильтрами. Обе команды только читают и
работают при открытом Codex.

```powershell
codexsync -c config.toml chats tree
codexsync -c config.toml chats list --text "parser" --limit 20
codexsync -c config.toml chats list --project none
```

`chats list` также принимает `--association`, `--since`/`--until`,
`--sub-threads` (потоки, порождённые агентами, по умолчанию скрыты) и `--json`.

Каждая строка говорит, *почему* чат находится там, где находится, и три причины
ведут себя по-разному:

| Метка | Связь | Значение |
|---|---|---|
| `pinned` — закреплён явно | `BOUND` | Явная запись в `thread-project-assignments`. Следует за проектом, если его путь меняется. |
| `by path` — найден по пути | `DERIVED` | Записи нет; записанная папка чата лежит под корнем проекта. При переносе проекта чат остаётся позади. |
| `by rule!` — только по правилу | `DERIVED_VIA_MAPPING` | Папка называет путь *другой машины*, и с проектом здесь её связывает только правило `[[path_mappings]]`. Codex эти правила не читает, поэтому показывает такой чат вообще без проекта. |

Последний случай — именно то, что даёт переезд между машинами: на ноутбуке
проект лежит на `C:`, а каждый чат, пришедший с настольной машины, по-прежнему
записывает `D:`. Показать ровно такие чаты:

```powershell
codexsync -c config.toml chats list --source-machine desktop --target-machine laptop --association DERIVED_VIA_MAPPING
```

## Перенос чатов в проект

Перенос начинается с предпросмотра. `chats move` ничего не пишет, пока вы не
повторите команду с напечатанным id плана, а для записи Codex должен быть
закрыт:

```powershell
codexsync -c config.toml chats move --chat 01a00ab4 --to LabTakt
codexsync -c config.toml chats move --chat 01a00ab4 --to LabTakt --confirm <plan-id>
```

- Файла плана нет: id покрывает решения *и* точные байты состояния, из которого
  они прочитаны, поэтому перестаёт совпадать, как только что-либо изменится.
- Запись — одна привязка на чат в той форме, которую использует обнаруженная
  схема, в том же конверте, что и любая другая запись: сначала проверенная
  полная резервная копия, проверка процесса непосредственно перед заменой и
  проверенный откат, если после неё что-то пошло не так.
- `--dry-run` выполняет все проверки и ничего не пишет.

## Ремонт после переезда на другую машину

Когда папка проекта переезжает — переименована, перенесена на другой диск или
открыта на второй машине под другим корнем, — Codex её теряет. Укажите правилом
[`[[path_mappings]]`](CONFIGURATION.md#path_mappings), где теперь находится
старый префикс, и просканируйте:

```powershell
codexsync -c config.toml repair-projects scan --source-machine desktop --target-machine laptop --save-plan repair-plan.json
codexsync -c config.toml repair-projects apply --plan repair-plan.json --confirm-plan <plan-id> --dry-run
codexsync -c config.toml repair-projects apply --plan repair-plan.json --confirm-plan <plan-id>
```

План строится из того, что на самом деле записано в сессиях, пропущенного через
правила соответствия. Проверочный запуск выполняет все отказы настоящего
применения, включая проверку процесса.

- **`REMAP_ROOT`.** Если *записанный* корень существующего проекта, пропущенный
  через то же правило, попадает в папку, на которую теперь указывают сессии,
  план меняет корень этого проекта, а не создаёт второй. Переписывается только
  это одно значение пути, поэтому у проекта остаются id и имя.
- **Смена корня никогда не применяется в одиночку.** Чаты, созданные до
  переезда, записали старую папку, и перенос корня из неё сделал бы их
  невидимыми. Поэтому каждая сессия, всё ещё лежащая под старым корнем, тоже
  закрепляется за проектом. Если какой-то такой чат остался бы без привязки,
  план сообщает `REMAP_ORPHANS_SESSIONS`, и применение отклоняется.
- **Два кандидата**, которые оба отображаются на один новый корень,
  сообщаются как `AMBIGUOUS_PROJECT`, и ничего не применяется.
- **Внутри файла сессии ничего не правится.** Сырые байты записи — её
  идентичность при сравнении веток, поэтому переписанный там `cwd` сделал бы одну
  и ту же историю на двух машинах навсегда расходящейся.

## Перенос файлов проекта

`project-move` сам переносит проект на одной машине:

```powershell
codexsync -c config.toml project-move scan --project LabTakt --to D:/Work/labtakt --save-plan move.json
codexsync -c config.toml project-move apply --plan move.json --confirm-plan <plan-id> --dry-run
codexsync -c config.toml project-move apply --plan move.json --confirm-plan <plan-id>
```

1. Проект копируется в папку, которой ещё не существует.
2. Хеш каждого скопированного файла сверяется с планом.
3. Проверенная копия переименовывается на место.
4. Только после этого меняется корень проекта и закрепляются чаты, которые
   попадали в проект по пути.

**Старая папка никогда не изменяется и не удаляется** — удалить её, проверив
копию, решаете вы.

Сканирование отклоняет цель, которая уже существует, лежит внутри проекта (или
проект внутри неё), пересекается с `.codex`, зеркалом, резервными копиями, temp
или хранилищами снимков либо принадлежит другому проекту, а также проект, в
котором есть символические ссылки, junction-точки или нечитаемые файлы.
Облачные заглушки (например, Яндекс.Диска) — обычные файлы, а не ссылки. Если
фиксация состояния не удалась после копирования, проверенная копия остаётся, и
новое сканирование её распознаёт (`copy_complete`), так что повторный запуск
только обновляет Codex.
