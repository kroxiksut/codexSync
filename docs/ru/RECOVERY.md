# Резервные копии и восстановление

[English](../en/RECOVERY.md) · **Русский** · [中文](../zh/RECOVERY.md)

[← Документация](README.md)

Каждая команда, которая пишет, делает проверенную резервную копию того, что
заменит, и ведёт журнал, пока работает. Эта страница о том и другом и о выходе
из записи, остановившейся на полпути. В окне это экраны
[«Резервные копии»](GUI.md#резервные-копии) и
[«Восстановление»](GUI.md#восстановление).

## Резервные копии

```toml
[backup]
backup_before_overwrite = true   # запись с false отклоняется
retention_days = 30
max_backups = 0                  # 0 = без ограничения
compression = "none"             # none | zip
```

- Резервные копии складываются в `paths.backup_dir` деревом каталогов (`none`)
  или одним `.zip`-файлом (`zip`).
- Каждая новая резервная копия несёт проверяемый манифест `codexsync-backup-v1`.
  Автоматическое восстановление выбирает только зафиксированные копии с
  манифестом.
- Резервные копии удаляются по `retention_days` и `max_backups` — только
  собственные снимки этой машины: не снимки другой машины, не папка, которая
  просто лежит в `backup_dir`, и никогда не снимок, нужный незавершённой
  операции этой машины для [`recover`](#прерванные-операции). Единственное
  исключение — **пакет конфликта (conflict bundle)**, проигравшая ветка
  расхождения сессии: он лежит в `semantic.root_dir` и никогда не удаляется,
  поэтому расходящаяся история никогда не остаётся единственной копией в том,
  что истекает.

## Восстановление из резервной копии

```powershell
codexsync -c config.toml backups list                                  # снимки и их имена
codexsync -c config.toml restore --dry-run                              # предпросмотр, ничего не пишет
codexsync -c config.toml restore --apply                                # последняя копия в локальную .codex
codexsync -c config.toml restore --from <snapshot-name> --apply         # конкретная копия (каталог или .zip)
codexsync -c config.toml restore --target cloud --apply                 # вместо этого в облачное зеркало
```

- Восстановление требует закрытого Codex и сначала делает резервную копию того,
  что заменит.
- Проверочный запуск сверяет каждый файл с манифестом копии.
- Старой копии без манифеста нужны явный `--from` и
  `--allow-legacy-snapshot`, и семантические пути (semantic-owned: сессии,
  индекс сессий, глобальное состояние) из неё восстановить нельзя.
- Копии, снятые версией 0.1, без манифеста — то есть как раз такие старые
  копии: только файлы настроек. Если нужно, чтобы восстанавливались и чаты,
  сделайте новую копию этой версией — синхронизация снимает её перед каждой
  перезаписью, а копия `.codex` ([Конфигурация](CONFIGURATION.md#копии-codex))
  хранит всё.

Чтобы вернуть `.codex-global-state.json` из снимка хранителя, см.
[Хранитель снимков → Восстановление из снимка](GUARDIAN.md#восстановление-из-снимка).

## Прерванные операции

`sync`, `restore`, `sessions apply`, `chats move`, `repair-projects apply`,
`project-move apply` и восстановление из снимка хранителя ведут долговечный
журнал. Если операцию прервать — пропало питание, принудительное выключение, —
журнал остаётся открытым, и каждая следующая запись отказывается начинаться,
пока он не закрыт. Эта блокировка и не даёт менять дальше наполовину применённое
состояние. Закрывают её две команды.

**Операция, остановившаяся до замены файлов, закрывается сама.** Журнал в
состоянии `PREPARED` или `BACKED_UP` доказывает, что ни один файл не заменён.
Обычная причина — облачный клиент держит файл журнала, пока выгружает его, и
запись, которая закрыла бы журнал, тоже получает отказ. Следующая запись на той
же машине закрывает такой журнал (в истории причина *Abandoned* — «прервана до
замены файлов») и идёт дальше. Решения по-прежнему ждут два вида: операция,
вошедшая в фазу записи (`COMMITTING`, `RECOVERY_REQUIRED`), и операция другой
машины — папка журналов лежит в общей рабочей папке, и та операция может ещё
идти.

**Посмотреть, что открыто** (без побочных эффектов):

```powershell
codexsync -c config.toml recover list           # открытые журналы и что закроет каждый
codexsync -c config.toml recover list --all     # и завершённые; --json для скриптов
```

В окне тот же список — страница **«Восстановление»**; синхронизация,
остановленная открытым журналом, предлагает кнопку **«Открыть восстановление»**,
которая ведёт прямо к этому журналу.

**Сначала прочитать доказательства** (без побочных эффектов):

```powershell
codexsync -c config.toml recover inspect <operation-id>
```

**Продолжение** — повторить прерванную команду:

```powershell
codexsync -c config.toml recover resume <operation-id>          # только отчёт
codexsync -c config.toml recover resume <operation-id> --apply
```

`resume` не воспроизводит потерянный план. Каждое место назначения заменяется
атомарно, поэтому после сбоя каждый файл либо полностью старый, либо полностью
новый, а повторный запуск исходной команды заново строит план по тому, что
действительно лежит на диске. `resume` проверяет, что резервная копия операции
цела, и закрывает журнал, чтобы команду можно было запустить снова.

**Откат** — восстановить резервную копию, которую операция сделала до первой
записи:

```powershell
codexsync -c config.toml recover rollback <operation-id>
codexsync -c config.toml recover rollback <operation-id> --apply
```

- Каждый файл возвращается на ту сторону, с которой он сохранён: одна
  синхронизация сохраняет файлы обеих сторон, и копия записывает сторону каждого.
  `--target` (`local` или `cloud`) необязателен; если он указан, это должна быть
  единственная сторона в копии, иначе откат отказывает, а не пишет файл не в тот
  корень. Он нужен только для `restore`, копия которого записана до того, как
  стороны стали записываться; такая копия от `sync` отклоняется — восстановите её
  вручную через `restore --from`.
- Глобальное состояние (после `chats move`, `repair-projects apply`,
  `project-move apply` или восстановления Guardian) возвращается той же
  осторожной записью, что и исходная: проверенная копия текущего файла,
  валидация, проверка процесса.
- `sessions apply` не откатывается: используйте `resume`, затем снова scan и
  apply. Перенос только продолжает историю или сохраняет заменённую ветку в
  пакете конфликта, поэтому повтор ничего не теряет.
- Обе команды по умолчанию выполняют проверочный запуск и требуют закрытого
  Codex.
- `rollback` проверяет всё, что может привести к отказу, — копию по её
  зафиксированному манифесту, стороны, корректность глобального состояния — до
  того, как освободить журнал, поэтому откат, который не может выполниться,
  оставляет блокировку на месте.
- Если копии, названной в журнале, больше нет (её удалило хранение по сроку,
  возможно, другой машиной с общей папкой копий), откат отказывает: что было
  заменено, доказать уже нельзя. `resume` журнал по-прежнему закрывает.
- Журнал, не дошедший до фазы фиксации, или копия без зафиксированного
  манифеста доказывают, что ничего не заменено — и то и другое записывается до
  первой замены, — поэтому откатывать нечего, и журнал просто закрывается.
- С одной папкой Codex одновременно работает только одна пишущая команда,
  какой бы она ни была; вторая останавливается с кодом `5`, а не перемешивает
  свои записи с первой.

## Когда Codex не запускается

```powershell
codexsync -c config.toml codex check
codexsync -c config.toml codex repair
codexsync -c config.toml codex repair --confirm-plan <plan-id>
```

`codex check` читает состояние Codex и перечисляет, что не так, кто бы ни был
виноват; в окне — *Восстановление → Состояние Codex → Проверить Codex*.
Проверка только читает и может идти при открытом Codex. У каждой находки указана
починка:

| Находка | Что значит | Починка |
|---|---|---|
| `CATALOGUE_REBUILD_STUCK` | Codex не запустится: пересборку списка чатов прервали посередине, и её никто не ведёт. Codex пишет «Не удалось загрузить настройки организации». | `codex repair` |
| `CATALOGUE_REBUILD_PENDING` | При следующем запуске Codex пересоберёт список чатов, пройдя все файлы чатов; не закрывайте его, пока не появятся чаты. | `codex repair` пропустит пересборку |
| `CATALOGUE_REBUILDING` | Codex пересобирает список прямо сейчас. | Не закрывать |
| `CATALOGUE_MISSES_CHATS` | Файлы чатов на месте, а Codex их не показывает. | `sessions catalogue` |
| `GLOBAL_STATE_MISSING`, `GLOBAL_STATE_INVALID` | Проекты, закрепления или привязки чатов к проектам пропали или оторваны. | `guardian restore` |
| `GLOBAL_STATE_UNRECOGNISED` | Глобальное состояние в форме, которую эта версия не знает (такую пишет Codex без проектов). На Codex это не влияет; проекты не переносятся, пока форма не известна. | Чинить нечего |
| `OPEN_JOURNAL` | Операция codexSync остановилась посередине и блокирует любую запись. | [Прерванные операции](#прерванные-операции) |

Как пересборка застревает: Codex собирает список чатов из файлов во время
запуска и открывается, только закончив. Если такой запуск прервать — окно
сдалось или Codex закрыли, — пересборка остаётся отмеченной как идущая, и каждый
следующий запуск ждёт её и завершается. `codex repair` возвращает её в состояние
«завершено»: одна строка, при закрытом Codex, после проверенной копии базы, с
журналом, как любая запись (семейство `codex-repair`). Если пересборку начала
просьба самого codexSync, возвращается ровно та строка, что была в копии,
снятой тогда. После этого Codex запускается с теми чатами, которые уже были в
его списке; пересборку можно снова попросить через `sessions catalogue`, когда
Codex можно будет оставить открытым до конца. `doctor` показывает то же
состояние в `codex_startup`.
