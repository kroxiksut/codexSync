# Командная строка

[English](../en/CLI.md) · **Русский** · [中文](../zh/CLI.md)

[← Документация](README.md)

```powershell
codexsync -c config.toml <команда>            # после установки
python -m codexsync -c config.toml <команда>  # из исходников, без установки
codexsync-gui.exe -c config.toml <команда>    # оконная сборка для Windows, без консоли
```

Общие параметры: `-c/--config` — путь к `config.toml`; `-v/--verbose` —
подробный журнал, в том числе какие процессы Codex были замечены;
`-V/--version` — напечатать версию и выйти: так можно спросить скачанный exe,
что он такое. `-h` у любой команды и подкоманды выводит её параметры.

## Все команды

«Холодная» — команда отказывается работать, пока Codex не закрыт. Остальные
только читают (или пишут вне `.codex`) и работают в любой момент.

проверенную резервную копию до того, как что-либо заменить.

## Начало работы

Записать шаблон в `config.toml` в текущей папке, по другому пути или поверх
существующего файла:

```powershell
codexsync init-config
codexsync init-config --output D:\codexSync\config.toml
codexsync init-config --output D:\codexSync\config.toml --force
```

Или сразу заполненный для этой машины. Он проверяется, все комментарии шаблона
сохраняются, `--machine-id`, `--local-state-dir` и `--workspace-root` задаются
вместе (`--cloud-root` — по желанию), а существующий файл в этом режиме не
перезаписывается никогда:

```powershell
codexsync init-config --output config.toml --machine-id laptop-1 --local-state-dir C:/Users/me/.codex --workspace-root D:/Cloud/codexSync
```

### Какая конфигурация открывается

`-c` называет файл, и указать несуществующий путь — это просьба создать его там.
Конфигурация может лежать в любой папке. Без `-c` поиск такой же, как в окне:
конфигурация, которую окно открывало последней, затем `config.toml` в текущей
папке, затем рядом с исполняемым файлом. Если файла нет нигде, команда
завершается с кодом 4 и объясняет, как его указать, — место за вас никогда не
придумывается. О файле, найденном не в текущей папке, сообщается, чтобы команда
никогда не работала молча с файлом, на который вы не смотрите.

Окно записывает путь к открытой или созданной конфигурации в маленький
файл-указатель — только путь, не содержимое:
`%LOCALAPPDATA%\CodexSync\config-path.txt` в Windows,
`~/Library/Application Support/CodexSync/config-path.txt` в macOS и
`$XDG_CONFIG_HOME/codexsync/config-path.txt` в Linux. Так команда без `-c`
находит тот же файл, что и окно. В скрипте или задаче расписания `-c` всё равно
лучше указывать явно.

Проверить конфигурацию, затем окружение:

```powershell
codexsync -c config.toml validate
codexsync -c config.toml doctor
```

`doctor` (и его двойник `preflight`) только читает и ничего не создаёт — тем
более внутри `.codex`. Он проверяет конфигурацию и каталоги, запущен ли Codex,
схему глобального состояния и последний восстановимый снимок, файлы сессий и
индекс сессий, каталог потоков в SQLite, что разрешено синхронизации, манифест
синхронизации, оставшиеся временные файлы, сможет ли Codex запуститься
(`codex_startup`: застрявшая пересборка списка чатов — провал, пока
`codex repair` её не вернёт) и то, не блокирует ли все записи незавершённая
операция (это провал, пока её не закроет `recover`).

## Окно из консоли

Всё, что делает окно, умеет и консоль: окно — это удобство, а у скрипта и у
задания планировщика есть только консоль. Страницы, у которых нет своей
команды, соответствуют так:

| Окно | Консоль |
|---|---|
| Главная | `summary` (`--recount` — пересчитать чаты и проекты сейчас) |
| Настройки — любое поле | `config set РАЗДЕЛ.КЛЮЧ ЗНАЧЕНИЕ`, `config unset РАЗДЕЛ.КЛЮЧ` |
| Настройки — правила путей | `config mapping list`, `suggest`, `add`, `remove` |
| Настройки — что синхронизируется | `config roots [ПУТЬ]` |
| Настройки — история | `config history` |
| Резервные копии | `backups list`, затем `restore --from ИМЯ` |
| Сессии — рабочий набор | `sessions scan --project/--chat --save-scope`; показать — `sessions scope` |
| *Всегда так* | `config set conflict.policy prefer_newer_mtime` (или другое правило) |
| Восстановление — состояние Codex | `codex check`, затем `codex repair --confirm-plan ID`; пересборка списка чатов — `sessions catalogue --confirm-plan ID` |

`config set` принимает значение TOML (`true`, `600`, `["sessions", "skills"]`);
текст можно без кавычек. Файл правится так же, как в «Настройках»: комментарии и
остальные значения остаются, результат проходит те же проверки, что и при
загрузке, файл, изменившийся тем временем, не перезаписывается, а прежняя
версия уходит в `config-history/`. Что окно править не даёт, консоль тоже
отклоняет — `safety.*`, `assumptions`, выключатели завершения процесса из 0.1 и
`handoff.root_dir`.

```powershell
codexsync -c config.toml config set conflict.policy prefer_local --dry-run
codexsync -c config.toml config mapping add --id laptop --source-machine laptop `
  --target-machine desktop --from C:/Users/me/Projects --to D:/Projects
codexsync -c config.toml backups list
```

## Коды выхода

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | ошибка выполнения |
| `2` | обнаружен конфликт, нужно решение |
| `3` | Codex запущен (не выполнено условие холодной операции) |
| `4` | неверная конфигурация или аргументы |
| `5` | безопасная остановка (fail-safe) |

`doctor`/`preflight` возвращают `0`, если все проверки прошли или есть только
предупреждения, и `5`, если хотя бы одна проверка провалена.

Неверная командная строка — неизвестный параметр, пропущенный аргумент — это
`4`, а не `2`, который обычно возвращает разбор аргументов: здесь `2` означает
конфликт. То же верно для `codexsync-gui.exe` с командой; на
`codexsync-gui.exe --version` и `--help` тоже отвечает командная строка.

`guardian restore` и `chats move` без `--confirm` — это предпросмотр; их
`--dry-run` проверяет всё, что проверила бы настоящая запись, включая проверку
процесса, только вместе с `--confirm`.

## Безопасность процесса

- codexSync никогда не запускает Codex и никогда не завершает его силой. С
  `[sync] close_codex = true` синхронизация просит приложение закрыться и идёт
  дальше, только когда проверка процесса его больше не видит; если оно не
  закрылось, синхронизация останавливается с кодом `3` и ничего не пишет.
  Старые флаги завершения отклоняются с кодом `4`, как и `allow_terminate_if_running = true` для пишущих
  команд.
- Запись требует, чтобы Codex был непрерывно остановлен две секунды, и ещё
  прямых проверок до и во время фиксации.
- С одной папкой Codex одновременно работает только одна пишущая команда, какой
  бы она ни была; вторая останавливается с кодом `5`.
- И `RUNNING`, и `UNKNOWN` блокируют запись. На macOS запись закрыта, пока
  определение процесса не подтверждено на живом Mac (см.
  [что пока не подтверждено](README.md#что-пока-не-подтверждено)).
- Если файл назначения на мгновение занят другим процессом (облачный клиент,
  индексатор поиска, антивирус), атомарная замена повторяется с ограниченной
  паузой. Проверка процесса повторяется перед каждой попыткой, а другие ошибки не
  повторяются ([D-011](../dev/DECISIONS.md)).
- Фоновые процессы, означающие «Codex всё ещё работает», перечислены для каждой
  ОС в
  [`process_detection.background_process_names`](CONFIGURATION.md#process_detection).
- С `-v` команды `plan`, `sync` и `restore` пишут в журнал отслеживаемые
  процессы: запущены ли Codex и его песочница, и подпроцессы Codex (PID, имя,
  родительский PID). Полные командные строки не собираются никогда.
