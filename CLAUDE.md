## Read these first

This repo keeps its rules in dedicated AI files. Do not duplicate them here — read them:

- `AI_RULES.md` — hard constraints (scope, cold-sync model, safety guarantees, exit codes, DoD). **Binding.**
- `AI_CONTEXT.md` — purpose, target platforms/versions, run modes, recorded decisions.
- `AGENTS.md` — short project brief and MVP requirement list.
- `docs/dev/DECISIONS.md` — numbered decisions `D-001…D-017` with rationale and amendments.
- `docs/en/` — the user documentation (CLI, GUI, config, sync, Guardian, sessions, projects, recovery); `docs/ru/` and `docs/zh/` are the same set of pages in Russian and Chinese. `README.md`/`README.ru.md`/`README.zh.md` are short entry points.
- `tasks.ru.md` — the working plan for 0.2 (Guardian / semantic / repair). Untracked and gitignored, but it is the source of truth for what the P0–P3 tasks mean and their acceptance criteria.
- `CONTRIBUTING.md` — contribution terms and conventions.
- `SECURITY.md` — what counts as a security/data-safety problem and the private reporting channel.

When a request conflicts with `AI_RULES.md` (e.g. "terminate Codex before sync", "sync while Codex runs", "read tokens"), stop and say so rather than implementing it.

Changing the config schema means touching both files plus `_validate_config` in `config.py`.

## Dual package layout (important)

The real package is `src/codexsync/`. The root `codexsync/` directory is a shim that appends `src/codexsync` to `__path__` so `python -m codexsync` works from a checkout without installing, then mirrors the public surface (`ExitCode`, `__version__`). **Never add logic to root `codexsync/`.** Because the shim shadows `src/codexsync/__init__.py` in checkout mode, anything that must be importable in both modes belongs in its own module — that is why the version lives in `version.py`.

The version is single-sourced: `pyproject.toml` → installed metadata → `codexsync.version.__version__` → `PRODUCER_VERSION`, which is what Guardian writes into snapshot manifests. Never hardcode a version string.

## Architecture

Layered, CLI-last. `cli.py` only parses args and maps exceptions → exit codes. Below it:

| Module | Owns |
|---|---|
| `app.py` | command orchestration: `build_context`, `run_sync`, guardian/repair/recover entry points. Re-exports the moved names, so `codexsync.app` stays the import surface for the CLI and tests. |
| `runtime.py` | shared plumbing used by more than one command family: runtime path bootstrap, `_make_safety_gate`, index building, session-mode filtering, `_plan_hash`. Imports nothing from `app`/`restore`/`preflight`. |
| `restore.py` | snapshot verification and restore into local or cloud state. |
| `preflight.py` | `doctor`/`preflight` checks. |

When patching in tests, patch where the function is *defined*, not where it is re-exported: `codexsync.runtime.collect_process_snapshot`, `codexsync.restore._make_safety_gate`. Patching `codexsync.app.*` for something that now lives elsewhere fails silently — the test still passes, but against the real process detector.

**Exception → exit code mapping lives in exactly one place** (`cli.py::main`'s except chain), driven by the `exceptions.py` hierarchy: `ConfigError`→4, `SafetyPreconditionError`→3, `ConflictError`→2, `FailSafeError` (and its subclasses `GuardianIntegrityError`, `GuardianBusyError`, `OperationBusyError`)→5. To make a new failure produce a given exit code, raise the right exception type — do not return codes from core.

### Safety spine

`safety_gate.py` is the single authority on whether an operation may mutate state. `OPERATION_PROFILES` classifies every `OperationKind` as read-only / mutating / side-effect free. Rules the rest of the code depends on:

- `UNKNOWN` process state is never optimistically treated as `STOPPED` — mutations fail closed with `FailSafeError`.
- A mutation requires a *continuously* stopped 2s window (`check(...)`), then a final direct check right before commit (`require(..., final=True)`).
- Callers must not implement their own bypass. `plan` runs while Codex is open but its result is marked `volatile` and cannot be reused by a mutation.
- A command finds `.codex` through `state_locator.locate_local_state_dir(cfg)` / `locate_state_dirs(cfg)`, never `detect_local_state_dir` directly. Loading compares codexSync's own folders (`config.external_roots`) with `paths.local_state_dir` *as configured*; when that folder is missing the locator falls back to `CODEX_HOME` or `~/.codex`, which loading never saw, so the locator re-checks every external root against the folder it actually found (CS-287).
- `DOCTOR` is `side_effect_free`: a diagnostic may read and report but must never create a file, least of all inside the Codex state directory. A 0.1 drift check that wrote probe files was removed for this reason (`D-010` amendment).
- `process_detector` answers "is Codex running" per platform, and `capability()` is the gate: Windows is the tested path, and macOS/Linux report `supported=False` until someone runs `docs/dev/experiments/process-detector-macos.md` and records it in `PROVEN_DETECTORS`. The POSIX matcher compares whole basenames (plus the 15-character truncation `ps -o comm=` produces on Linux), and an entry containing `/` is a *path* marker matched against the command path — which is how `ChatGPT.app/Contents/MacOS/` is told apart from the ordinary ChatGPT app, since the desktop build was renamed `ChatGPT` in July 2026 while keeping the bundle id `com.openai.codex`.

codexSync never starts or stops Codex. Legacy termination flags/config are rejected with exit 4 (`_require_mutation_compatible_config`). The one exception is a *request* (`D-029`, `codex_closer.py`): with `[sync] close_codex = true` a sync that finds Codex open asks the app to quit -- Restart Manager without `RmForceShutdown` on Windows, gated by `PROVEN_CLOSERS` -- waits for the gate to see it gone, and otherwise refuses; the watcher (`run_handoff(close_codex=False)`) and dry runs never ask. Never add a forced path.
- A transient lock on a destination (`WinError 5/32/33`, `EACCES/EBUSY/ETXTBSY`) is retried with bounded backoff by `fs_replace.replace_with_retry` — `SyncEngine` passes `before_retry` to re-prove the process check before each attempt; anything else raises on the first attempt. Every replace into codexSync's own folders (journals, manifests, handoff/peer boards, Guardian, semantic store, plans, `config.toml`) goes through it too: a cloud client opens each file it is told about, and a journal transition that failed on that left the journal open and blocked every later mutation. `commit_global_state` uses it with `before_retry` re-proving the gate *and* re-hashing the live file, so a wait never ends in overwriting a state that moved. A bare `os.replace` remains only in log rotation, where a refused rename means another process claimed the file. Do not widen that error set — a retry is only correct while the operation stays atomic (`D-011`).

`app.commit_global_state` is the single envelope for editing `.codex-global-state.json` (repair apply and chat move both go through it): operation lock, journal, verified full backup, gate re-checked immediately before the replace, and a verified rollback from that backup if anything after it fails. A caller decides *what* to write and proves it valid; it does not get to decide how carefully the write happens. Every failure before the replace closes the journal as `FAILED` (via `RECOVERY_REQUIRED` once `COMMITTING`), and the live file is re-hashed against `original` immediately before `os.replace` — a journal left open by a refused gate blocked every later mutation (CS-291).

A mutating command (`sync`, `restore`, `repair-projects apply`) always runs the same envelope, wired in `app.py::run_sync` / `restore.py::restore_from_backup`:

`OperationLock` (non-stealable, per state-root+machine) → `JournalStore.begin` (`mutation_journal.py`, payload-free durable evidence) → backup-first via `BackupManager` → `after_backup`/`pre_commit`/`before_replace_check` callbacks into the gate and journal → `SyncEngine.execute` (each payload staged in the folder of its own destination, then `os.replace`) → manifest rewrite → `COMMITTED`. A crash between `COMMITTING` and `COMMITTED` leaves `RECOVERY_REQUIRED`.

`OperationLock` is one lock per (state root, machine) for **every** family — sync, restore, sessions, each `commit_global_state` caller and state backup; restore locks the local root even for a cloud target. Re-entry exists only with `reentrant=True` in the same thread (`recover rollback`). Never key it by family again: two families each passed the non-atomic check in `begin()` together (CS-304).

`JournalStore.begin` refuses to open a new journal while an earlier one is non-terminal — that block is the protection, and `recovery.py` is the sanctioned way out of it (`recover list|inspect|resume|rollback`), raised as `RecoveryPendingError` (exit 5, code `RECOVERY_PENDING`, so the window links to that journal). One exception, and it is narrow on purpose: given `machine_id` (every caller passes it while holding this machine's `OperationLock`), `begin` first closes this machine's journals still at `PREPARED`/`BACKED_UP` as `FAILED`/`Abandoned` (`close_abandoned`) — they prove nothing was replaced, and a refused journal write on the way out (a cloud client uploading it) left one open on 2026-10-06. Ownership is `owned_by`: the recorded `machine_id`, else the snapshot name (`snapshot_belongs_to`, the same rule `BackupManager.prune` uses). Never widen it to `COMMITTING`/`RECOVERY_REQUIRED` or to another machine's journal — the journals folder is in the shared workspace and that run may still be going. Two invariants make it work, and both are load-bearing: `SyncEngine.execute` stamps the backup manifest *before* the first replace (so an unstamped snapshot proves nothing was overwritten), and `begin()` records the snapshot name in the journal (so rollback never has to guess which backup was its own). Each backup manifest entry records its `side` (written by `SyncEngine`), and rollback puts each entry back into its own root; `--target` is optional and must name the only side a snapshot holds (an old snapshot without sides needs it, or is refused for a sync). Rollback follows the family and is proven **before** the journal is closed: files through `restore.execute_restore_plan`, the global state through `commit_global_state`, `sessions` never. A journal in `PREPARED`/`BACKED_UP` proves nothing was replaced; a recorded snapshot missing after `COMMITTING` is a `FailSafeError`, never "nothing to roll back". `_rollback_refusal` feeds both the refusal and `can_rollback`. `COMMITTING` has no direct edge to `FAILED`; close it via `RECOVERY_REQUIRED` so the trail keeps saying the commit phase was entered. The journal is also the sync history (`recovery.list_history`, `codexsync history`, the window's History tab — every family, since one full sync is three journals: `sync`, `sessions`, `project-sync`, each with its own counts): `counts`, `origin`, `finished_at_utc` and `failure` (an exception *class*, never its message) are descriptive, read leniently, and never consulted by a gate — a malformed one is dropped rather than making the journal unreadable, because an unreadable journal blocks every mutation.

### Sync path

`state_locator` → `scanner`/`filters` → `runtime._build_indexes` → `planner.build_sync_plan` (timestamp first, SHA-256 only when ambiguous) → `models.SyncPlan` → `sync_engine.SyncEngine`. `manifest.py` persists the previous two-sided fingerprint so a one-sided change can be distinguished from a conflict. Conflict handling is policy-driven (`conflict.policy`); a conflict the policy does not resolve raises `ConflictError` before any write, whatever the policy.

A payload is staged **beside its destination** (`.<name>.<token>.codexsync.tmp`), never in `paths.temp_dir`: `os.replace` is atomic only within one filesystem, and the two are routinely on different drives — the cloud folder on one, `.codex` on another — which made every write into `.codex` fail with `WinError 17` while the suite, whose sandbox is one volume, stayed green (CS-253). Nothing is overwritten before the whole set is staged and proven, so the guarantee is the one the temp directory used to carry. A killed run's siblings are swept from the folders the next run writes into, by name and only once they are an hour old, because two machines may be staging into one cloud mirror.

The sync manifest keeps one baseline **per machine** (`machines.<id>.files`, id = `runtime.sync_machine_id`): the local and cloud fingerprints as *that* machine last saw them. It lives in the shared workspace, and a single unkeyed baseline made machine B read A's fingerprint as its own and push its stale file over A's newer one on every handoff (CS-288). Never read another machine's entry as this one's, and never attribute the pre-0.2 unkeyed `files` table — its first run is a first sync. Any conflict in a plan stops `sync` whatever `conflict.policy` is; `propagate` never deletes out of an include root the other side holds nothing of, and case-only path collisions are conflicts. An empty/`.`/`""` `include_roots` is refused, the scanner never falls back to the whole directory, and `SECRET_NAMES` (`runtime.py`) is filtered at any depth in `_build_indexes`. So is every compiled program (`native_programs.is_native_program`, by header — PE/ELF/Mach-O, since Mac programs have no extension; `D-021`), in `_build_indexes` and in `.codex` copies alike: a program goes stale, is restored by an installer, and a copy from another machine is useless or downgrades it. `BackupManager.prune` removes only this machine's own snapshot names and never one an unfinished journal names; cloud, backup, temp and `manifest_file` may not overlap.

`sync.direction` (`D-012`) and `sync.delete_policy` (`D-013`) both hang off the manifest, and both are only safe because of it. A one-way run records the paths it did not act on in `plan.skipped`, and `build_manifest` carries their **previous** entry over unchanged — recording what the skipped side looks like now would tell the next bidirectional run that the two sides had agreed, after which it falls back to mtime and the older file wins for good (`tests/test_sync_direction_and_deletes.py` plays that out). `propagate` deletes only where the previous manifest proves both sides held the file and the surviving side has not moved since; anything else is a conflict, the first run after switching it on deletes nothing, and the backup is written and verified before the removal, in the same envelope, so `recover` can put it back.

`filters.PathFilter` translates a glob itself instead of calling `PurePath.match`, where `**` means the same as `*`. Under the old behaviour the shipped `**/tmp/**` matched `a/tmp/b` and matched neither `tmp/arg0/lock` (no segment before `tmp`, which is exactly where `.codex/tmp/` sits) nor `a/tmp/b/c` — so the exclusions in the template excluded almost nothing. There were no tests for that module at all; there are now.

A session file carries a `session_meta` record *per resume*, not one per file — 54 of 252 on the machine this was built against, up to 298 in one file. Only the identity has to agree across them (`RESUMED_SESSION`); two different ids in one file is `CONFLICTING_SESSION_META` and invalid. Treating a repeat as damage dropped 267 MiB of 864 MiB out of `catalog.valid` — never mirrored, never listed, no error — and `chats tree` showed 98 chats instead of 152. Anything that decides a session is invalid costs exactly that much silence, so check it against a real `.codex` before adding one.

Paths under `sessions/`, `archived_sessions/`, `session_index.jsonl`, global project state and SQLite are **semantic-owned** (`runtime._is_semantic_owned`) and are excluded from generic mtime copying — never "fix" this by re-adding them to the copy plan. `sync_candidates.list_sync_candidates` lists one level of both sides for the settings tree: it reports those paths *with* their reason rather than hiding them, and it never returns a credential file at all, so no screen can offer one by mistake.

A long read takes a `progress(phase, done, total)` callback (`progress.py`). The total comes from walking the tree, which is cheap, before the hashing, which is not; a callback that raises never fails the read, because the caller asked for a catalogue, not for a number. `session_catalog.scan_sessions` unpacks compressed branches in a small thread pool (`SCAN_WORKERS`; xz releases the GIL) while plain ones stay on the calling thread (JSON parsing holds it — threads made `.codex` slower), and `scan_both_sides` reads `.codex` and the mirror at once; both keep the found order, so the catalogue never depends on timing (CS-354).

### Guardian (0.2, runs while Codex is open)

`guardian_schema.py` holds one adapter per runtime family, tried in order, and the winner's `schema_id` is recorded in the snapshot manifest. Add a new adapter for a new shape; never loosen an existing one, because a state that two adapters could claim is a state whose meaning is guessed. `supports_project_creation` and `build_binding_value` exist so the repair writer follows the detected schema rather than assuming the legacy one.

This is where the worst bug of 0.2 lived: the desktop build's bindings (`projectKind`/`projectId`) matched no adapter, so every real state was quarantined and `latest-good` never existed — Guardian was inert on real data while every test passed against fixtures encoding the assumed shape. The same fault had a second instance in `repair_plan`, which read project roots from `root`/`path`/`cwd` keys the Electron build does not use (it keeps them in `rootPaths`) and compared an object-shaped binding to a bare id: on a real state it recognised 0 of 16 projects. Both were found the same way and by nothing else — **when touching anything schema-shaped, run it against a real `.codex-global-state.json`, not only fixtures.** Reading a root or a binding goes through `guardian_schema` (`project_root_paths`, `binding_project_id`, `replace_project_root`) so there is one place that knows each shape; `doctor` reports the detected schema and the restorable snapshot for the same reason.

Read-only observation of `.codex-global-state.json`, writing only into an external Guardian root that config validation forces to be outside `.codex`/sync/backup/temp. Split: `guardian_models` (contracts) → `stable_reader`/`guardian_runner` (3 stable reads, polling, fallback scan) → `guardian_validation` + `guardian_schema` + `guardian_shrink` (bytes/JSON/referential integrity/suspicious shrink) → `guardian_store` (staging → `COMMITTED` → `latest-good` pointer, quarantine, retention) → `guardian_lock` (single writer per machine). Ordering is by monotonic `generation`, not wall clock; a snapshot is visible only after `COMMITTED`; nothing suspicious can become `latest-good`. A new generation is one above every generation any manifest/`COMMITTED` marker in the machine directory declares, and above the pointer's; a file that exists but cannot be read fails the commit — skipping it reissued a number and froze the store for good (CS-297). Generations may have gaps. A snapshot's predecessor is `latest-good` (what it was judged against), and only a payload equal to `latest-good` is `UNCHANGED`. `watch` survives store errors (log + back off); uncommitted snapshot directories are swept by name and age only; quarantine keeps the first and newest event per drop (`drop_key`).

…on its own. `guardian_accept.py` (`D-014`) is the one way a *person* moves the baseline past a real shrink — without it a real drop freezes `latest-good` forever, because every later state is compared with the pre-drop baseline (this machine, since 2026-09-13: Codex re-created all 16 projects under new ids). Three limits carry it: only `SUSPICIOUS` with a shrink code is acceptable — or `INDETERMINATE` solely because the baseline's schema differs or is missing while the state fully validates under a known adapter (`BASELINE_SCHEMA_CHANGED` → `SCHEMA_CHANGE_ACCEPTED`) — never `INVALID` or an unrecognised state; the explanation is counts only, so names, roots and thread ids still never leave core; and the plan id pins the *drop* (baseline, counts, codes, digest of which bindings went and why), not the state bytes — an id that followed the bytes could never be confirmed while Codex rewrites the file. The commit is the store's ordinary one, marked `SHRINK_ACCEPTED`, and retention keeps both it and the baseline it overrode. The preview uses `guardian_pointer.find_latest_good`, which never rebuilds the pointer.

### Session transfer (0.2, CS-224)

`semantic_merge` classifies two branches of one session by streaming both files; `semantic_transfer` turns that into a frozen `TransferPlan` whose id covers every decision. Three rules carry the safety and none is negotiable: a divergence is never merged or interleaved — it produces a conflict id, and one whole copy is kept: by a recorded resolution, else by the configured rule (`D-027`: `conflict_rule_for(policy, direction)`, frozen into the plan as `conflict_rule`/`direction`, `RESOLVED_BY_RULE`; `newer` compares `last_record_at` as moments and ties stay `RULE_CANNOT_DECIDE`), else it blocks — and the loser goes whole into the conflict bundle either way; a resolution is pinned to both branch hashes, so a branch that moves afterwards makes it `STALE_RESOLUTION`; and raw bytes decide record equality, with canonical JSON consulted only where it is provably unambiguous (no floats, NFC strings only) so two different records can never collapse.

`sessions apply` reuses the sync envelope wholesale, and two details are load-bearing. The plan id covers every decision but *not* the creation timestamp — including it would make each rebuild differ from the plan it checks, so the freshness check could never pass. And a branch that loses a resolution goes into a conflict bundle under `semantic.root_dir`, not just the backup: backups are pruned by `backup.retention_days`, so without the bundle the sole copy of a divergent history would expire on a timer. An archive move is applied (`D-023`): the side that no longer holds the state this machine's own semantic manifest entry records is the one that moved (no entry → follow the mirror), the branch is written where the followed side keeps it and the old file is removed through `SyncPlan.deletions` (backed up and verified first; `MOVES_BRANCH`), and into `.codex` the catalogue must name the moved file. Archived on one side and continued on the other is a conflict (`ARCHIVED_AND_CONTINUED`). `transfer_direction` is the one place that says which side an item writes. A duplicate session id is settled by `prefer_catalogued_copies` when the catalogue names exactly one copy (`STALE_DUPLICATE_BY_CATALOG`, CS-348). It is *not* how a paged chat is read: Codex 0.160 continues a long chat in `rollout-…-<id>_<id2>.jsonl` whose `session_meta` has the same id plus `history_base` (`thread_id`, `end_ordinal_exclusive`), and CS-348 mistook that page for a stale copy — a false `DIVERGED_NO_COMMON_RECORDS` that stopped every sync and a first part never mirrored (CS-356). A page is its own branch, keyed by `SessionDescriptor.branch_key` (`<id>#page-<n>`); every grouping, hash, manifest entry and bundle id goes through `branch_key`, the catalogue row places the whole chain (`chain` in `_catalogue_objection`), and chat-level readers take `one_per_chat`/`latest_page`.

`PROVEN_LAYOUTS` is the second empty gate, mirroring `PROVEN_CONTRACTS`. A source filename says where a branch lived on *another* machine; placing it wrongly here makes the session invisible with no error at all. Fill it only from `docs/dev/experiments/session-layout-adapter.md`.

A template is rendered with `state`, `source_dir`, `file_name` and `session_id`, and empty segments collapse. `source_dir` is not decoration: a real machine has two shapes at once — 228 active branches under `sessions/<year>/<month>/<day>/` and 23 archived ones flat in `archived_sessions/` — so a template able to name only the folder and the file renders 176 of 196 sessions to a path the thread catalogue does not name (`CATALOG_PLACES_ELSEWHERE`), which is the same dead-on-real-data failure as Guardian's. Check a template change by rendering it against a real state directory and comparing with `read_thread_placements`, never against fixtures alone.

Two things decide a write besides the layout, and both were dead parameters until they were fed. `sqlite_audit.read_thread_placements` reads `threads.id/rollout_path/archived` (never `title`, `preview` or `first_user_message`) and a write into `.codex` is refused unless the catalogue already places that branch at exactly that path — on an observed machine all 195 sessions have a row naming their rollout file, so the file system is not the whole truth and a branch put elsewhere is invisible with no error. `SESSION_NOT_IN_CATALOG` is the honest meaning of `UNSUPPORTED_STATE_BACKEND`: making the runtime see a *new* session needs a row codexSync will not write. `PlacementStatus.ABSENT` (no catalogue at all) constrains nothing; `INDETERMINATE` blocks, and the two must never be collapsed. Rollout paths come back as `\\?\C:\...` for a good fraction of rows — strip the extended-length prefix or 39 of 250 threads look unplaceable.

A copy that cannot be read is not a copy that is absent. `build_transfer_plan` groups *every* descriptor by session id; a session with an INVALID/AMBIGUOUS copy on either side, or a failed comparison, is `BLOCKED_INVALID_BRANCH` — nothing written on either side, no conflict id, and deliberately **not** in `_UNRESOLVED_TRANSFER_BLOCKS` (no recorded choice repairs a file, and blocking every apply would freeze the mirror). A write for a session the destination lacks is refused when any container variant already sits at the target (`DESTINATION_OCCUPIED`); a mirror write for a session the mirror holds goes to that copy's own path and container (`MIRROR_PATH_KEPT`). `FORMAT_MIGRATION` is set only on `DIVERGED*`. A working set that expands to nothing is `scope_matches_nothing` (hashed only when true), never an empty `scope`, which means "everything". A thread catalogue that exists but cannot be read is `INDETERMINATE` (`CATALOG_UNAVAILABLE`), never `ABSENT`; `canonical_digest` is `None` for a record with a repeated key.

`semantic_store.py` holds two things that are deliberately different in kind. The **manifest** is metadata: one atomically replaced, self-verifying JSON file per (machine, session) under `manifest/<machine>/<session hash>.json`, recording the branch hash, record count, state, parent and the base an agreement established. It feeds `confirmed_bases`, which is what makes `ARCHIVE_TRANSITION` reachable instead of a permanent `MISSING_BASE`. A **conflict bundle** is the one place a full payload is kept, because the losing branch's only other copy is a backup that retention expires. It lives at `conflicts/<conflict_id_for(...)>` — the id the user resolved — its copies are re-hashed before `COMMITTED`, and bundles under the old name are found by verification, never renamed.

The manifest never stores a session payload, and that is a decision, not an omission: `semantic.root_dir` may sit in the user's cloud folder, nothing prunes this store, and copying every reconciled session would upload the whole session directory (777 MiB on the machine this was built against) and grow per edit forever. An earlier `publish()` did exactly that and was removed. Do not reintroduce payload copies outside conflict bundles without asking.

The commit shape is one self-verifying file replaced in a single step, not a payload plus a separate `COMMITTED` marker: in a folder a cloud client syncs on its own schedule two files can arrive in either order or half-written, while one file whose `entry_digest` covers its own contents cannot be half-believed. An entry also claims its own machine and session, so a copy that lands in another directory is refused rather than adopted. Peer entries are accepted only when the digest verifies and the generation has not gone backwards for that machine — the guard is against a cloud client restoring an old copy, not a hostile writer.

Canonical record checkpoints are the one field from the task that is deliberately absent: computing them means streaming hundreds of megabytes to write digests nothing reads yet. Add them when something proves a prefix relation from the manifest instead of from the files.

`jsonl_codec.py` is the one place that knows a branch may sit in a container. The mirror stores each branch compressed (`semantic.mirror_compression`, default `xz`, about a third of the size on real data); a branch written back into `.codex` never is. The rule that makes this safe is that compression is a property of the container and never of the history — every hash, record count and comparison comes from the decompressed stream, which is why reading goes through `open_jsonl` and not `path.open("rb")`. `SyncEngine._stage_verified` keeps its proof by hashing what the staged container *decompresses to*, so a compressor that loses a byte fails before any destination is touched. The codec is in the mirror layout id and therefore in the plan id: an apply writes the container the confirmed plan named, never what the config says now. Per branch and not one archive — an archive of 778 MiB would be re-uploaded whole after one session grew by a line, and would have to be unpacked before the remote side could be classified at all.

Two rules keep a container from costing a session. The mirror's codec applies only to a branch the mirror does not hold yet — a branch already there keeps its container (`MIRROR_CONTAINER_KEPT`), because the container is part of the file name, `delete_policy` is `never`, and `rollout-x.jsonl` beside `rollout-x.jsonl.xz` is one session id under two names, which the catalogue drops as `DUPLICATE_SESSION_ID` for good. And `CopyAction.codec` is `None` for every ordinary copy: transforming is opt-in, so a user's `notes.jsonl.gz` under an included root is never unpacked because of its name. Reading a container also fails outside `OSError` (`EOFError`, `LZMAError`, `zlib.error`) — catch `JSONL_READ_ERRORS`, since a half-written file is the normal state of a cloud-synced mirror.

The gate covers exactly one destination: a directory the Codex runtime reads. A write towards the cloud mirror is not gated (`MIRROR_LAYOUT_ID`, `mirror_relative_path`) — nothing but codexSync reads that copy, so a branch keeps its own relative path, and gating it left the mirror with no way to be rebuilt at all, since sessions are semantic-owned and never copied by plain `sync`. Consequently `sessions apply` is partial by design: `_UNRESOLVED_TRANSFER_BLOCKS` (conflict, target collision) refuses the whole plan because each names a user decision, while layout- and SQLite-blocked items are logged and left alone. Do not widen that set to every blocked action — that is the state the mirror could not be written from.

The layout gate has one exception, and it is narrow on purpose (`D-019`, CS-330a): a branch whose session this machine already holds is written over that very file (`IN_PLACE`) when the catalogue names exactly that path for that thread, both copies are active or both archived, the catalogue's archive flag agrees with the folder, and the local file is plain JSONL (`_in_place_refusal`). No path is rendered, so nothing about the layout is assumed. Here `PlacementStatus.ABSENT` *refuses* (`IN_PLACE_CATALOG_ABSENT`) — without a row nothing shows the runtime finds the chat by that file. A session this machine never held stays `BLOCKED_UNPROVEN_LAYOUT`; do not extend in-place to it by guessing a path.

A session this machine never held is written into `.codex` by default — carrying it is the point of the tool (owner, 2026-10-03; `keep_in_cloud` opts out): `[semantic] new_chats = "same_path"` (`D-020`, the default in the loader, both templates and the window) builds the plan under `SAME_PATH_LAYOUT_ID` — the source path relative to `.codex`, as 0.1 copied it — and waives exactly one check, the missing catalogue row (`SESSION_NOT_IN_CATALOG`), since that row is what Codex has to add; every other catalogue objection and `DESTINATION_OCCUPIED` still refuse, and each item carries `NEW_CHAT_SAME_PATH`. It is not a `PROVEN_LAYOUTS` entry (evidence is the owner's 0.1 observation, and `backfill_state` says Codex filled its catalogue from files once, in March), so `doctor`'s `session_visibility` counts chat files the catalogue does not list — that count is the proof.

That proof came back negative on 2026-10-04 (laptop: 197 written, `not_listed=197`, every project "no chats"): Codex fills `threads` from the files only while `backfill_state.status` is not `complete`. `thread_catalogue.py` (`D-024`) is the **one** SQLite write codexSync makes: `backfill_state` back to the row Codex's migration creates (`pending`, watermark cleared), in one transaction that re-checks `complete`, under `SESSION_APPLY`, lock, journal family `thread-catalogue` and a verified backup of the database — and only when a chat file is unreachable through the catalogue (id unknown, or the catalogued file gone), at most once per set of files (`ALREADY_ASKED`, marker in `temp_dir/thread-catalogue/`). Codex then writes every row itself. Never write a `threads` row; the evidence is Codex 26.930's own SQL, read from `codex.exe`. `run_handoff` runs it after projects; `sessions catalogue` runs it alone.

The second and last SQLite write is a chat's name (`chat_names.py`, `D-025`): names live only in `threads.name`, never in the file, so carried chats showed their first message. Each machine publishes the names it shows to `chat-names/<machine>.json`; a sync sets a peer's name only where the name here is unset (`NULL`, `''`, or equal to `title`), with Codex's own rename statement guarded by the value the plan saw. Both writes share `app._write_codex_catalogue`. The per-machine boards after `project_sync` (names, project files) use `peer_board.py`.

`project_files.py` (`D-026`) compares project *folders* — never carries them: each full sync publishes per project the git commit/branch/uncommitted digest or, for a plain folder, every file with its size, SHA-256 and mtime (the owner asked for a file list; hashes cached per machine), and warns when the other machine had more. Git runs with `GIT_OPTIONAL_LOCKS=0` (a status must not rewrite a user's index), a folder an enclosing repo ignores is plain (the test sandbox sits inside this repo), and a failing check never fails a sync.

**A history does not only grow** — Codex itself broke that (`D-015`). The September 2026 desktop build rewrote every session file into numbered records (`ordinal`), kept each mtime, and dropped rolled-back turns and repeated `session_meta` on the way, so a mirror written before it conflicts on every session. The catalogue records `record_format` and `last_record_at` per branch; a conflict between two formats is labelled `FORMAT_MIGRATION` and **stays a conflict** — never prove it away as "same history re-encoded", the dropped records contradict that. `sessions resolve --format-migrations` is one explicit decision for all of them, and it never decides `OLDER_FORMAT_HAS_LATER_RECORDS`. The loser goes to `superseded/<sha256>/` compressed and alone, not into a two-branch conflict bundle (242 sessions would have been ~2 GB into the cloud). Keep that directory one level deep: two 64-character levels hit the 260-character Windows path limit inside the test sandbox.

A branch bound for `.codex` whose working folder (mapped through `[[path_mappings]]`) is not a directory here carries `CWD_ABSENT_HERE`. It blocks nothing and is in the plan id; `build_transfer_plan` only checks when given `folder_exists`, so plans built without it hash as before.

### Chats (0.2)

`chat_directory.py` answers "which chats exist and which project is each one in", and `chat_move.py` writes one `thread-project-assignments` entry per chat through `app.commit_global_state`. Three rules carry it.

A chat is told apart from a thread an agent spawned **structurally** — `parent_thread_id`, or a `thread_source` that is not `user` — never by reading the records. About half the session files on a real machine are spawned threads, so this decides what the list even contains, and a text heuristic would reclassify a chat the day someone quotes the wrong sentence in one.

The *reason* a chat sits under a project is reported, not just the project. `BOUND` follows a project that moves; `DERIVED` (cwd under `rootPaths`) is left behind by it; `DERIVED_VIA_MAPPING` means only a `[[path_mappings]]` rule connects them, and since Codex does not read those rules such a chat is invisible in the app until it is bound. Never fold that third value into `DERIVED` — it is the list of chats a machine handoff stranded.

A move has no plan file. The plan id hashes the decisions **and the exact state bytes**, so the id printed by a preview stops matching the moment anything changes, which is the same freshness guarantee `--confirm-plan` gives elsewhere without a file to leave lying around.

### Repair / machine handoff (0.2)

A read-only SQLite open is not automatically a read-only *file* operation, and this is the one place the project's hardest rule was being broken. SQLite creates `-wal`/`-shm` for a WAL database when they are absent, and rebuilds a stale `-shm` when the log is empty — in C, so `tests/test_guardian_state_isolation.py` cannot see it. `sqlite_audit._read_only_connect` therefore picks the connection from whether the log holds frames: none → `immutable=1` (creates and rebuilds nothing), frames + `-shm` → plain `mode=ro`, frames without `-shm` → refuse as `WAL_WITHOUT_SHARED_INDEX` and report `INDETERMINATE`, never `ABSENT`. Never add a bare `sqlite3.connect` here. A library's writes are only visible by listing the directory before and after (`tests/test_sqlite_creates_nothing.py`), not by intercepting calls.

`session_catalog` (streaming read-only session scan) + `path_mapping` (named-machine prefix rules from `[[path_mappings]]`) → `repair_plan` builds an immutable, hashed plan. `repair-projects apply` refuses to run unless `--confirm-plan` matches the plan id exactly.

The remap cover never takes a chat from another project: a session under the old root already bound (in the plan or the state) to a different project is left alone and reported as `REMAP_SESSION_BOUND_ELSEWHERE`, and apply refuses a plan binding one session to two projects (`conflicting_bindings`). Where `supports_project_creation` is false the planner emits `SKIP_NO_PROJECT` (no write, no binding), never `ADD_PROJECT` — five chats outside every project made every real plan unappliable (CS-303).

`REMAP_ROOT` is how a project that moved keeps its chats. Evidence for it is narrow on purpose: an existing project qualifies only when its *recorded* root, run through the same mapping the sessions use, lands on the root those sessions now point at. Two candidates are `AMBIGUOUS_PROJECT`, not a pick. Applying it rewrites that one path value through `replace_project_root` and leaves names, ids and timestamps alone — which is why a remap is allowed on the Electron schema where `supports_project_creation` is false: it invents nothing. **Never migrate a path by rewriting `cwd` inside session JSONL** — raw bytes are a record's identity in `semantic_merge`, so that would make one history on two machines permanently `DIVERGED`.

**A remap is never emitted alone**, and this is the load-bearing part. How a thread reaches a project is not settled: on a real state 93 desktop chats have no `thread-project-assignments` entry at all and are reachable only by their `cwd` falling under a project's `rootPaths`, while 6 do have one — including a chat whose `cwd` stopped matching after its project moved, which is Codex itself writing an override for exactly this case. Under the first reading, replacing the root detaches every older chat, silently: the chat simply stops appearing. So `_bind_sessions_left_behind_by_a_remap` pins every session under the old root to the project with an explicit binding, and `_remap_orphan_codes` re-checks the cover and emits `REMAP_ORPHANS_SESSIONS` if one was missed (a non-empty `plan.codes` refuses the apply). Correct under both readings, which is why neither has to be settled first. Do not "simplify" by dropping either half.

Do **not** make a remap add the new root to `rootPaths` instead of replacing it. The field is a list, but every project ever observed has exactly one entry, so a second element is a guess about cardinality — the same class of guess that made Guardian inert.

The working set (`session_scope.py`) narrows what a transfer may write **into `.codex`** to a chosen set of projects and chats — a project means all of its chats, including the sub-threads they spawned and the ones that appeared on the other machine since. The cloud mirror is never narrowed: `_apply_scope` leaves `FAST_FORWARD_REMOTE` alone, so the backup cannot become partial, and a held-back branch becomes `OUT_OF_SCOPE`, which blocks nothing and keeps `WOULD_BE_<action>` in its codes. The set is part of the plan id, an **empty** set is left out of the hashed material entirely (so every pre-existing plan keeps its id), and the stored file in `plans/` holds the chosen names, never the expansion — a frozen list of session ids would stop covering tomorrow's chat.

`session_index.py` is wired **read-only**: `sessions index` (`app.audit_session_index`) reports both sides and their divergences, and `doctor` carries the same check. Its write path stays gated on `PROVEN_CONTRACTS`, see below. `semantic_store.py` and `semantic_merge.py` are wired through `sessions apply`.

`session_index.py` is gated on purpose. The index is an append/update journal, and how the Codex runtime reduces a repeated id — last line wins, or max `updated_at` — is not knowable from the file. The two readings differ exactly when a clock ran backwards, which is the case this project exists for, so both are computed, disagreement is reported as `REDUCTION_AMBIGUOUS`, and `render_session_index` refuses while `PROVEN_CONTRACTS` is empty. Do not populate that dict from reasoning: it is filled only by running `docs/dev/experiments/session-index-contract.md` against disposable state, and the entry records the Codex version it was observed on. Reading is not gated and must not become so — the audit is what tells a user *why* nothing is written, and it is the only thing that exercises this module against a real index (191 records for 151 sessions on the machine it was checked against).

### Copies of `.codex` (`D-017`)

`state_backup.py` takes a verified zip of the valuable part of `.codex` into `[state_backup] root_dir`, which only the user chooses (empty = off; a schedule without it is a `ConfigError`, and it may not overlap `.codex`, backup, temp, the cloud mirror, Guardian or semantic roots, since each has an owner that prunes or mirrors it). Selection is `VALUABLE` (sessions, archive, global state + `.bak`, SQLite catalogues by pattern with `-wal/-shm`, index, `config.toml`, rules, skills, memories, automations); `SECRET_NAMES` is refused at any depth. It goes through the gate as `OperationKind.STATE_BACKUP` — `requires_stopped` but not a mutation — with `wait=True` polling until Codex closes (the task: `state-backup create --wait`, `STATE_BACKUP_SLOT`, 24 h OS limit over a 23 h own limit); a file whose size/mtime moves while read fails the copy, the archive is written as `.partial`, re-hashed, gate re-checked, then renamed, and only then are this machine's copies beyond `keep` pruned by exact name. The window's *Make a copy now* never waits. Restore is by hand on purpose.

### Handing work between machines (`D-018`)

`codexsync sync` at `[sync] scope = "full"` (the default, `D-028`) *is* `run_handoff`, and its dry run is `preview_full_sync`, which builds the same plans through `_full_sync_chat_plan`; `scope = "settings"` is the old files-only `build_context`/`run_sync`. `handoff.py` is the record, `app.run_handoff`/`watch_handoff` the orchestration, `notifications.py` the only channel to a person who is not watching. Each machine writes **only its own** self-verifying file in `[handoff] root_dir` (inside the synced workspace, never inside the cloud mirror); "has this machine loaded A's work" compares handoff **ids**, never two machines' clocks. Another machine's handoff counts as delivered when every file its fingerprint names (size + SHA-256, keyed by a hash of the path) is in the cloud copy — the cloud client is never asked. A run is one full sync nobody decides: the chat plan is built and checked **first** (a conflict `[conflict] policy` leaves open, or a target collision → `ChatDecisionsNeeded` before any write — exactly the Sessions page's "needs a decision" category, CS-349), then settings through `build_context`/`run_sync`, then `apply_session_transfer` with the plan's own id. The record is written only after both halves; projects, chat names and the catalogue request follow, each applying the plan it builds (`planned_here`), and one that fails is logged and reported in `steps_not_done` (`HANDOFF_STEPS`) — it never costs the record of halves already delivered, and the next sync redoes it. and a new handoff id only when this run wrote to the cloud copy — a load-only run keeps its old id, or every other machine would wait for a "delivery" of what it holds. While `PROVEN_LAYOUTS` is empty only a chat this machine already holds reaches `.codex` (in place, `D-019`) plus, by default, a chat it never held (`new_chats = "same_path"`, `D-020`, counted as `new_chats_written`); `chats_not_loaded` counts the rest so nothing says "loaded" about work that stayed in the mirror. The watcher reacts only to `RUNNING`/`STOPPED` the gate is sure of (`UNKNOWN` is neither), never ends its loop on an error, and its task has no OS time limit (`PT0S`, `TimeoutStartSec=infinity`). Notification texts are `notify.*` keys in the window's language files, read as data by core (core may not import the GUI package); `NOTIFY_KEYS` must exist in every language.

### Projects between machines (`D-022`)

`project_sync.py` carries the sidebar — `local-projects`, `project-order`, `pinned-project-ids`, `thread-project-assignments` — and nothing else of `.codex-global-state.json` (the rest is per machine: window bounds, remote-control ids, `*-by-host` migration markers). Each machine publishes its list to `<manifest_file folder>/projects/<machine>.json` (self-verifying, written only by that machine, bindings as *legacy* ids because app-server ids are per host); `app.sync_projects` merges pending peers through `commit_global_state` (`OperationKind.PROJECT_SYNC`, family `project-sync`) and then republishes. Rules: match by id, then root through `[[path_mappings]]`; add the peer's entry verbatim; **never remove**; peer pins/order/bindings win for shared projects only from a publication whose content id is not yet in this machine's `accepted`. An empty project list is claimed by the legacy adapter, so `require_carried_schema` treats it as electron-v2. `run_handoff` runs it last; the window's *Synchronise* runs `run_handoff` (`Controller.handoff_now`), not `run_sync`. `[handoff] root_dir` empty means `handoff` beside the manifest (CS-335). SQLite is not written; whether Codex shows a project *added* to the JSON after `projectsMigrated` is still to be seen on the second machine.

### Project move and Guardian restore

**Projects also live in `state_*.sqlite`**, which codexSync never writes (`project_registry.py`, gate `PROVEN_PROJECT_REGISTRY`, empty). So `project_move` and `REMAP_ROOT` rewrite `rootPaths` in the JSON only and leave `project_roots.path` as it was, and whether the runtime follows that is unverified — `doctor` says so on every run, and deleting or merging a project is not offered at all. `docs/dev/experiments/project-registry-contract.md` is what would settle it.

`project_move.py` moves a project's *files*: copy into a folder that does not exist, re-hash every copy against the previewed inventory, rename the verified staging directory into place, then remap the root and pin the chats that reached the project by path through `app.commit_global_state` (`OperationKind.PROJECT_MOVE`). The old folder is never modified or deleted, and the only thing the module may delete is its own staging directory, proven by name and an internal marker naming the plan. A failed commit keeps the copy plus a resume marker beside it, and a rescan reports `copy_complete`. The module takes `rebuild`/`require_stopped`/`read_state`/`commit_state` callables so it never imports `app`; `app.apply_project_move_plan` wires them. On a real Yandex.Disk checkout 13 of 18 projects were reparse points that are *not* links (cloud placeholder tags) — `fs_links.is_link` refuses only symlinks, junctions and name-surrogate tags; never widen it back to "any reparse point". It is the one link rule for `project_move`, `state_backup` and `session_catalog`: `is_symlink()` misses junctions (`.codex/skills` holds them, and the `.codex` copy followed them out of the folder), and `os.path.isjunction` does not exist on 3.11. The resume marker is written before the rename and the staging marker removed only after it, so every crash point is recoverable by a rescan. Every path under a root goes through `_fs` (`\\?\` on Windows): the staging name adds ~40 characters, which pushed a 219-character `.git` path past 260 and failed the move with `WinError 3` on a machine with long paths off (2026-10-06); `_remove_tree` clears read-only bits because git objects are read-only and `copy2` keeps that. A staging directory of an earlier plan is removed only when its marker names this very `new_root`. Guards comparing paths (`forbid_writes_under`, the move tests' `_norm`) strip the prefix with `plain_path` — without it a write in `\\?\` form slips past them.

`guardian_restore.py` plans putting a verified, committed snapshot of this machine back; `app.restore_global_state` applies it through `commit_global_state` (`OperationKind.GUARDIAN_RESTORE`). It refuses a snapshot that fails today's validation, one in another schema than the live file (`SCHEMA_CHANGED`), a live file whose project keys are in no known shape (`LIVE_SCHEMA_UNKNOWN`), and a missing live file (the envelope's first step is a backup of it). Planning is read-only: it never rebuilds the latest-good pointer.

`guardian_schema._validate_references`: a project the order omits is `PASS_WITH_WARNING` (`PROJECT_NOT_IN_ORDER`) for `electron-v2` only. The desktop build writes such states itself (observed 2026-09-13), and holding it to the legacy complete-order rule quarantined every snapshot and made every state commit refuse its own result. An order naming a missing project, a duplicate in the order and a broken binding stay invalid; `legacy-v1` keeps the complete-order rule.

### GUI (optional extra)

`src/codexsync/gui/` is a second shell, not a second implementation. The console is the first: every core call the controller makes must be used by `cli.py` too or be listed with its reason in `tests/test_cli_parity.py::WINDOW_ONLY`, and the keys neither may edit are one list, `config_edit.NOT_EDITABLE`. Qt is allowed only in `window.py`, `widgets.py` and `screens/`; `controller.py`, `i18n.py`, `theme.py` and `__main__.py` import without it, and `__main__.py` reports a missing toolkit as exit 4. The controller calls only public `app.py` names — which is why `app.py` re-exports the config editor, automation and the read-only listings — and `tests/test_gui_boundary.py` reads every GUI module's imports against `FORBIDDEN` (the mutation envelope plus `config_edit` and `system_scheduler`), with a planted-import test so the guard cannot silently stop firing. It matches module *names*, which is why the recovery screen lives in `screens/journals.py`: a module called `recovery` trips it.

Two properties are load-bearing. The window's "Codex is closed" line is **advisory and labelled as such**: the real refusal happens inside `app.py` against a check taken at the moment of the write, so a stale banner authorises nothing, and `codex_looks_stopped` is true only on an explicit `PASS` (a `WARN` covers both running and undetermined). And a mutation is always plan-then-id, exactly as on the CLI — the confirm dialog quotes the plan id, and restore/resume/rollback unlock only after a dry run of the same choice.

Each screen is a *model* (plain state that survives rebuilds) and a *screen* (disposable widgets with `render()`). Switching language, theme or config rebuilds every screen from its model; `MainWindow.run(page, call, apply)` applies a finished job to the model and redraws whichever screen exists then. Jobs come back through `widgets.JobRunner`, a QObject slot, because a signal connected to a plain callable runs in the worker thread. Tests pass `runner=` with one that runs inline and replace `window.confirm`. `_Job` turns anything a call raises into `Failure.UNEXPECTED`, so a write's `apply` checks `outcome.ok` before unpacking. A same-file save bumps the window's generation: a *read* started before it is delivered as `STOPPED_SAFELY` (`activity.stale`) and the visible page re-activates, so a plan built under the old rules never lands; writes deliver their real outcome and are never cancellable (storing a working set is a write). No page scans on arrival — Projects included (`ArrivalDoesNotScanTests`); the one read the window starts by itself is the project-folder check once per start (`D-026`, owner's choice). Trees are rebuilt only when their data object changes, never per progress tick.

No widget holds a sentence. Every string comes from `gui/locale/<lang>.json` through `gui/i18n.py` (Qt-free, English fallback, CLDR plural forms per language in `PLURAL_RULES`); adding a language is adding a file. `tests/test_gui_i18n.py` checks key parity, plural completeness, placeholder parity, that every key-shaped string constant in the drawing modules exists, that computed keys exist for every value of the core enums they are built from, and that every check `preflight.py` emits has a label. Colours and geometry come from `gui/theme.py`, a transcription of `assets/design/design-tokens.json` that `tests/test_gui_theme.py` compares against. The displayed brand is `CodexSync` (`gui.BRAND_NAME`); the package and CLI stay `codexsync`. The window keeps only its size, last page and language in `QSettings`; the path of the config it last opened goes into the pointer file (`config_locations.write_config_pointer`, `%LOCALAPPDATA%\CodexSync\config-path.txt`) so the CLI finds the same file — never a launcher flag, never the *content* of `config.toml`, and never a window position: a restored position is what opened the window off the screen edge, so `place_within_screen` shrinks to the work area and centres instead. Which config an argument-less start opens is `config_locations.choose_config_path` (pointer → cwd → beside the exe), and when none exists there is **no** config: never propose a location on the user's behalf. An invented `%APPDATA%` path once made every page run against a file nobody created (CS-268); now pages other than first run/about show `screens/no_config.py` until a file is opened or created. `gui/locations.py` also finds an existing workspace by folder names alone.

Home (`screens/home.py`, first page, beside Overview) draws one tile per thing kept from `home_stats.read_home_summary`, which opens no session file and reads each part on its own (a failed part is one tile, `errors[part]`). Chat/project counts need the full scan, so they come from a counts-only cache in `config_locations.cache_dir()` (`%LOCALAPPDATA%\CodexSync\cache`, one file per config) written by every `Controller.chats` scan and by *Recount* — never scanned on arrival. `Controller.home` and `codex_backups` are patched in the GUI test harness like `automation`: with a real controller they reach `schtasks` and the process list.

Settings and Automation both edit `config.toml` through `screens/config_form.py::ConfigFormScreen` (draft, check, confirm, save — one implementation). Automation (`screens/automation.py`) holds `[scheduler]`, `[state_backup]` and `[handoff]`; Settings no longer has that tab. Settings edit `config.toml` through `config_edit.py`: a line-based editor whose every edit is re-parsed with `tomllib` and must equal the intended dictionary (so a comment-preserving edit can never silently mean something else), a save that validates with the CLI's loader plus `_require_mutation_compatible_config`, refuses on a changed base sha, and keeps the replaced file in `<workspace>/config-history/` — never under `backup_dir` (pruned by age) or `temp_dir`. The screen emits an edit only for a value that differs from the file, and `safety.*` is displayed but never editable. Automation is `[scheduler]` applied by `automation.py` to `system_scheduler.py`'s user-level OS task; the periodic job can only be `guardian_snapshot|preflight|sync_dry_run`. It repeats every 30 minutes by default and never more often than every 5 (`MIN_SCHEDULER_INTERVAL_SECONDS`): it is a safety net, not a watcher. The page edits that period in minutes through `Field.scale`, while the file keeps seconds. A true/false config value must be a TOML boolean (`_bool_value`): `bool("false")` is True. Two tasks mutate. `sync_at_login` (`D-016`): `sync --apply --unattended` in a task of its own (`LOGIN_SYNC_SLOT`), once at sign-in, conflicts decided by `conflict.policy` like any run (`D-027` amended the old forced `manual_abort`; `--conflict-policy`/`handoff_now(conflict_policy=…)` override it for one run). And the handoff watcher (`D-018`, below), which replaces it. Never widen either to restore/repair, and never let installing one run it. `automation.py` takes all four adapters (`scheduler`, `login_scheduler`, `backup_scheduler`, `handoff_scheduler`) injected or none (a lone fake left the other slot on real `schtasks`), and no test may run the real `schtasks`/`launchctl`/`systemctl`/`powershell` — adapters take an injected `run`. Schtasks output is localized on the target machine, so status is read from `/XML` and `Get-ScheduledTaskInfo` JSON, never from its column headers.

Screenshots offscreen need `QT_QPA_PLATFORM=offscreen` **and** `QT_QPA_FONTDIR=C:/Windows/Fonts`, or every glyph renders as a box. The documentation screenshots (`docs/screenshots/<lang>/`) come from `scripts/docs_screenshots.py`, which sets both and drives the window with `DemoController` — invented data, a temporary demo config shown as `D:/Cloud/codexSync/config.toml`, and the first-run probes patched. Never regenerate them from a real config: the status bar, the first-run screen and every table would publish real paths, project names and chat titles.

A sentence that sends the person to another place ships with a button that goes there: `MainWindow.go_to(page, target)` switches the page and calls `Screen.reveal(target)` — a Settings tab id or a `section.key` field, which is scrolled to and focused (CS-351). A full sync's notes and their buttons are one implementation, `screens/sync.py::full_sync_notes`/`ResultLinks`, shared by *Synchronisation* and *Automation*. Every key of the shipped template must be a field on some page or be listed with its reason in `tests/test_gui_config_reach.py::NOT_SETTINGS` (CS-352).

Never block Qt by editing `sys.modules` inside the suite. Clearing `codexsync` out of it and re-importing leaves every later `patch("codexsync.runtime.…")` aimed at a different module object; the first attempt at that test turned a 42-second suite into 27 failures over 8 minutes. The check runs in a subprocess instead.

## Tests

`tests/conftest.py` explains why sandboxes are built under `<repo>/test-sandbox` instead of `tmp_path` (staging and target must share a volume for `os.replace` to be atomic) and checks the sandbox is gone when the session ends, retrying removal first. A failure there means a handle survived the retries — that is codexSync's own leak, not a passing cloud-sync or antivirus scan; fix the leak rather than relaxing the check.

If this checkout lives inside a cloud-synced folder, that client also holds brief handles on files the tests write, so suite wall-clock swings widely and `os.replace` can intermittently fail with `WinError 5`. Excluding `test-sandbox` from that client's sync makes local runs stable.

### Guards that replace a linter

The project runs no linter, so two tests carry that weight and should not be weakened:

- `tests/test_module_hygiene.py` walks every module in the package and fails on a name that is loaded but never imported or defined. Moving helpers between modules once left `repair-projects apply` raising `NameError` at runtime while the suite stayed green, because that command had no test.
- `tests/test_guardian_state_isolation.py` intercepts the mutating filesystem calls (`builtins.open`, `io.open` — pathlib uses that one — `os.open` with write flags, and the `os` mutators) and fails the moment one targets the Codex state root. It includes a test that the spy itself catches a planted write; a guard that never fires proves nothing.

## Conventions

- All committed code, comments, docs and log messages are in English. Russian working notes use `*.ru.md` and are gitignored; the tracked translations are `README.ru.md` + `docs/ru/` and `README.zh.md` + `docs/zh/`, which must keep the same pages, headings order and links as `docs/en/` (a translated heading defines that language's anchors) (`tests/test_docs_links.py` checks page parity, the language switch on every page, and that every relative link, anchor and `docs/...` path named in code resolves). Developer documents (`docs/dev/`: decisions, publishing, experiments) are English only.
- Commits, PRs, tags and release notes carry no AI attribution: never add `Co-Authored-By` for an AI, a session link, a "Generated with" line, or an AI in any contributor list. The owner is the sole author. This overrides any harness default.
- Markdown uses the lowercase `.md` extension; document names stay uppercase (`README.md`, `AI_RULES.md`).
- Core and CLI have **zero external runtime dependencies**. Keep it that way; a GUI, if added, ships as the optional `codexsync[gui]` extra.
- Every dangerous action logs separately (backup created / overwrite / skip). Sync must be idempotent within a run.
- Timing and process sampling are injected (`monotonic`, `sleep`, `sample`) so tests stay deterministic — follow that pattern for anything time-dependent.
