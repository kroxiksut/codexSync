# Интерфейс codexSync

Эта папка — исходные материалы для реализации графического интерфейса. Все
видимые пользователю надписи — на русском языке; не переводятся только имя
программы Codex, имена файлов, пути и значения формата конфигурации.

## Источник истины

Все рабочие настройки хранятся только в `config.toml`. Графическое приложение:

1. читает файл в черновик;
2. проверяет черновик тем же загрузчиком конфигурации, что и командная строка;
3. показывает различия;
4. сохраняет новый файл атомарной заменой, предварительно поместив прежний
   проверенный файл в историю конфигурации вне `.codex`;
5. после сохранения сбрасывает все открытые планы и требует сканировать заново.

В отдельном хранилище интерфейса допустимы только размер окна и последняя
открытая вкладка. Там не должно быть путей, правил, политик синхронизации или
любых настроек, которые меняют поведение codexSync.

## Общий каркас

- `assets/brand/brand-mark.png` — чистый знак без надписи. Он расположен слева;
  название приложения выводится справа от него в одну строку.
- `assets/brand/brand-lockup.png` — готовая композиция знака с надписью; использовать
  её только там, где требуется единое изображение бренда, а не в шапке окна.
- `assets/brand/codexsync.ico` — значок приложения Windows из чистого знака;
  содержит 16, 20, 24, 32, 40, 48, 64, 96, 128 и 256 пикселей.
- Боковая навигация: «Обзор», «Первый запуск», «Синхронизация», «Привязка
  чатов», «Сессии», «Проекты», «Хранитель снимков», «Резервные копии»,
  «Восстановление», «Настройки».
- Использовать цвета и отступы из `design-tokens.json`.
- Кнопка состояния или зелёная строка не разрешает запись сама по себе. Решение
  о записи принимается только основным слоем приложения непосредственно перед
  изменением файлов.

## Проверочный запуск

Единое пользовательское название режима `dry_run`: **«Проверочный запуск»**.
Он строит и проверяет план, выполняет все безопасные проверки, но ничего не
копирует, не заменяет и не записывает в состояние Codex. Он должен быть виден
в сценариях синхронизации, переноса сессий, ремонта проектов, восстановления и
отката. Настоящее применение плана — отдельная кнопка после проверки.

## Экраны

### Обзор

Показывает проверку окружения, состояние процесса Codex, доступность каталогов,
снимка состояния и индекса сессий. Обновление только ручное.

### Первый запуск

Создаёт `config.toml`, задаёт уникальное имя текущей машины, локальную `.codex`
и каталог синхронизируемого зеркала. Не создаёт и не изменяет состояние Codex.

### Синхронизация

Показывает план направлений «облако → локально» и «локально → облако».
«Проверить план» ничего не записывает. «Синхронизировать» заново строит план
через защитный шлюз, поэтому нельзя применять устаревший экранный результат.

### Привязка чатов

Это не окно общения. Оно показывает, под каким проектом находится каждый чат
и почему: закреплён явно, найден по пути, найден правилом соответствия или не
имеет проекта. «Построить план автопочинки» выбирает только однозначные связи;
неоднозначные связи остаются без изменений и требуют выбора проекта.

### Сессии

Показывает классификацию веток: совпадают, могут быть перенесены, требуют
решения, не поддерживаются. Расходящиеся истории никогда не объединяются.
Перед применением нужен сохранённый план и его точный идентификатор.

### Проекты

Показывает дерево проектов, их корни и количество привязанных/потерянных
чатов. Есть два разных сценария:

- «Ремонт после перехода на другую машину» — строит существующий точный план
  ремонта привязок по путям сессий и правилам соответствия.
- «Переезд проекта» — `C:\Temp → D:\Project`. Если файлы уже перенесены,
  графическое приложение может позднее предложить безопасно поменять путь в
  состоянии Codex по подтверждённому плану. Перенос самих файлов проекта и
  обновление пути — новая возможность, отсутствующая в текущем основном слое;
  её нельзя имитировать кнопкой до отдельного протокола резервирования,
  межтомного переноса, отката и восстановления после прерывания.

Истории сессий при переезде проекта не переписываются.

### Хранитель снимков

Показывает снимки `.codex-global-state.json`. Снимок разрешён при открытом
Codex: читается только устойчивое состояние, а файл снимка создаётся лишь вне
`.codex`, зеркала, резервных и временных каталогов.

### Резервные копии и восстановление

Отображает только проверенные снимки. Восстановление начинает с проверочного
запуска; настоящее восстановление требует закрытого Codex и создаёт новую
резервную копию перед заменой файлов.

### Восстановление после прерывания

Если журнал не завершён, все новые мутации заблокированы. Экран сначала
показывает доказательства, затем предлагает только допустимые журналом
операции: продолжение или откат в явно выбранную цель.

### Настройки

Подразделы повторяют конфигурацию, а не создают второй формат:

- основное: `identity`, каталоги текущей машины и зеркало;
- синхронизация: сравнение, конфликты, состав синхронизации, запрет удаления;
- защита и снимки: остановка Codex, безопасная остановка при неопределённости,
  настройки хранителя `.codex-global-state.json`;
- автоматизация: запуск после входа в систему, период, режим и состояние
  пользовательской задачи планировщика;
- пути проектов: направленные `[[path_mappings]]`;
- резервные и служебные данные: срок хранения, временный каталог, журналы,
  история `config.toml`.

### Автоматизация

Это отдельный подраздел настроек, а не скрытая опция синхронизации. Его цель —
избавить пользователя от повторяющихся ручных запусков, не ослабляя правила
безопасности.

- «Запускать после входа в Windows» создаёт пользовательскую задачу в
  «Планировщике заданий Windows», а не службу и не запуск самого окна.
- «Период проверки» задаётся в минутах. Минимум — одна минута для обычной
  проверки/синхронизации; для снимка хранителя поддерживается отдельный
  интервал от 60 секунд.
- Режим по умолчанию — «Проверочный запуск»: он формирует отчёт и журнал, но
  ничего не копирует и не записывает.
- «Снимки состояния» разрешены при работающем Codex и записывают только
  проверенные снимки вне `.codex`.
- «Синхронизация» включается только явным подтверждением. При каждом запуске
  всё равно действует защитный шлюз: Codex должен быть закрыт, до замены
  создаётся резервная копия, а при неопределённости задача безопасно
  останавливается.
- Автоматизация никогда не применяет ремонт проектов, перенос сессий,
  автопочинку привязок чатов, восстановление или откат: для этих операций
  нужен отдельный сохранённый пользователем план с точным идентификатором.
- Экран показывает последнее выполнение, следующее выполнение и понятную
  причину пропуска. Готовность облачного хранилища не проверяется — это
  остаётся ответственностью пользователя.

`config.toml` остаётся источником истины для желаемой конфигурации
автоматизации. Задача Windows — лишь применённое представление этих настроек
в системе. В реализации нужно расширить раздел `[scheduler]` полями режима и
запуска после входа, а графическое приложение должно само создавать,
обновлять, проверять и удалять пользовательскую задачу. Существующий
`task.config.ps1` не должен становиться вторым источником настроек.

### Контракт `[scheduler]`

Для CS-232 закреплена единая для Windows, macOS и Linux схема:

```toml
[scheduler]
enabled = false
mode = "guardian_snapshot" # guardian_snapshot | preflight | sync_dry_run
interval_seconds = 60
run_at_login = true
startup_delay_seconds = 0
jitter_seconds = 0
```

`interval_seconds` не может быть меньше 60. `guardian_snapshot` делает один
проверенный снимок состояния; `preflight` только проверяет условия; 
`sync_dry_run` строит и проверяет план без копирования и записи. Значения для
реальной синхронизации и любой другой мутации недопустимы. Каждый адаптер
планировщика преобразует эту схему в пользовательскую задачу своей ОС, не
добавляя операционных параметров в отдельный файл.
